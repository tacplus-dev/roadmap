# Kernel state path translation — findings

Paths below are relative to `/Users/jody/workspace/gitlab/secondstarcavalier/schematic/`.
`KCG` = `platform/services/kernel/codegen/src/main/resources/templates/`.

## Verdict

**There is a clear, single choke point, and the translation is a kernel-codegen-only change of modest size — with one hard prerequisite that is NOT in the kernel state layer.**

- Kernel state is a flat `Map<String, Proto>` per boundary, one Hazelcast map per `(state root, field)`. Keys are opaque caller-supplied strings; there is **no hierarchical path and no tenant anywhere in the key or the map name today**. A "chroot" is therefore a *key-prefix rewrite* (`key -> "/<tenant>" + key` on ingress, strip on egress), not a path-tree operation.
- Every state RPC (Get/Put/Set/Remove/Delete/ContainsKey/GetAll/KeySet/Size/Clear/PutIfAbsent/Watch, plus the store server's Put/Get/Delete/List) is rendered from ~20 fragment templates in ONE generator (`BackendServiceServerGenerator` + `BackendStoreServerGenerator`), and every one of them starts with `checkAccess(...)` where the caller's gRPC `Context` is in scope. That is the choke point. In-process kernel writers (TenantAdmin, ClusterStatePublisher) bypass gRPC and hit `BackendMap` directly — they are `/system` and need no rewrite.
- Watch is a full-snapshot poll every 500 ms (server re-serializes the whole map to every watcher), not a delta/eventbus stream. Filtering+stripping the snapshot per watcher is straightforward; no eventbus fan-out carries state keys.
- Rough size: ~14 kernel fragment templates + the poll/watch renderer in `BackendServiceServerGenerator.java` + a small `NamespaceScope` helper; **zero tacplus-generator changes** for the data path (the wire proto shape does not change; Rust/Java state clients are untouched because they already replace their cache wholesale from the returned `entries` map).
- **What is NOT transparent**: (a) keys that are also record fields (`(spec.indexed)`, `store_key`, `instance_keyed` composite ids, `ProjectConfigEntry.project_namespace` = `"/tenant/project"`) — a naive key strip leaves the payload untouched, which is *correct* as long as the kernel prefixes only the map key and never the field; (b) singleton boundaries (`Singleton.SINGLETON_KEY`) need the same treatment or a tenant-owned service silently shares the singleton with every tenant; (c) topics and queues have no key at all and would need per-tenant Hazelcast object names, not key prefixes; (d) `Query`/`WatchQuery` are declared on the wire but have no kernel implementation, so nothing to rewrite yet.
- **Prerequisite outside this scope**: today `SecurityAuthenticator` puts only `caller-service`, `caller-service-path`, `caller-instance-id` in the gRPC Context — **no namespace claim** — and `Spiffe.classify` only recognises a SERVICE when `segs[0]=="system"`, so a `/<tenant>/services/<name>` subject would fail `servicePath()` and be rejected UNAUTHENTICATED before any state RPC runs. The translation layer needs the identity agent's work to (1) parse tenant-rooted service SPIFFE IDs and (2) surface a `caller-namespace` Context key.

## 1. State key/path model

**Keying.** A `(spec.service_state)` root (e.g. `kernel.ConfigState`, `platform/proto/services/kernel.proto:1084`) is decomposed into boundaries; each `repeated` field becomes a collection with a `map<string, T>` wire shape and each scalar-message field a singleton. tacplus emits the backend service proto in `tacplus/pkg/internal/proto/state.go`: collection RPCs at `:656-670`, and the request/response messages at `:806-836` — `GetRequest{string key = 1}`, `PutRequest{string key = 1; T value = 2; int64 lock_counter = 3}`, `EntriesResponse{map<string, T> entries = 1}`, `KeysResponse{repeated string keys = 1}`. The key is a bare string with no structure.

**Storage.** Kernel-side, the generated `BackendMap` opens one Hazelcast map per boundary named `CLASS_NAME + ":" + mapName` (`platform/services/kernel/codegen/.../generator/BackendMapGenerator.java:54-63`; the map name is the fully-qualified generated class, per the template doc at `KCG/BackendMap.java.template:20-21`). Key type is `String` (`.../kernel/graphs/IMap.java:44-46`). Collection get/put/delete are direct `Map.get(key)/put(key,v)/remove(key)` (`KCG/fragments/statemap_collection_get.java.template`, `statemap_collection_put_convergent.java.template`, `statemap_collection_delete.java.template`). Singletons use a fixed `Singleton.SINGLETON_KEY` (`KCG/fragments/server_singleton_get.java.template:6`).

**Where the tenant appears today: nowhere in the key or map name.** The only tenant-bearing things are record *fields* chosen per-message:
- `Tenant.name` `(spec.indexed)` (`kernel.proto:1046`); `TenantConfigEntry.tenant_name` (`:1059`); `ProjectConfigEntry.project_namespace` = `"/tenant/project"` (`:1071-1074`). Kernel's own TenantAdmin writes these with the namespace *string as the map key* (`configMap.putTenants(ns, tenant)` at `.../cluster/TenantAdminServiceImpl.java:106`, `putTenantConfigs(ns, entry)` `:256`, `putProjectConfigs(ns, entry)` `:288`) — so for ConfigState the key happens to be the namespace, by convention of that one writer, not by the store.
- `(spec.store_namespace)` (`tacplus/pkg/proto/sys/spec.proto:1987-2006`) and `owner_spiffe`-style fields are **record-store (stratum) concepts** for `(spec.record)` messages, filtered on egress by the *service's own* generated wrapper — not by kernel state. `platform/todo/MULTI_TENANCY_PLAN.md:279-299` confirms the data-plane model is "owner_spiffe on every persisted record; OPA is the filter; no tenant_id filter below OPA" — i.e. the plan never contemplated key-level isolation in kernel state.
- `(spec.instance_keyed)` (`spec.proto:1731-1734`) is the one place the kernel builds a key from caller identity: `serviceId + "@" + instanceId`, and it also **overwrites the `id/service_id/instance_id` fields in the payload** (`KCG/fragments/server_collection_set_instance_keyed.java.template:9-38`). This is the closest existing precedent for "server-authoritative key derived from Context".

**What `(spec.namespace)` actually does.** It is a *request-field* annotation on ordinary service RPCs, enforced in the generated **service wrapper of the callee service**, not in kernel: resolve caller's `namespace` claim; empty -> stamp, equal -> pass, different -> INVALID_ARGUMENT. Rust: `tacplus/pkg/internal/rust/types/namespace_gen.go:84-108` (`caller.namespace()` -> `rustRequestNamespaceBlock`). Java: `tacplus/pkg/internal/java/types/servicewrapper_gen.go:1655-1663` calls `javaPredicateNamespacePin` (`recordnamespace_gen.go:262-290`), reading `Auth.verifiedTokenFromContext().getNamespace()`. The claim value for a service token is `SpiffeIds.namespaceFromSpiffe(subject)` (`.../cluster/IdentityServiceImpl.java:1383-1386`), which for `spiffe://td/system/<loc>/services/x` is `/system[/loc]` (`tacplus/pkg/templates/java/chassis/spiffe/Spiffe.java.tmpl:498-507`). So "stamps `/system` for S2S" is a consequence of the SPIFFE path, not a hardcode. **None of this touches the kernel state servers**: `SecurityAuthenticator` never reads the namespace claim (`KCG/SecurityAuthenticator.java.template:328-333` puts only service name, service path, instance id in Context).

## 2. Where a translation layer would sit

**Single choke point: the generated `<Root>BackendServiceServer` RPC bodies.** Every state RPC is rendered from a fixed fragment list in `platform/services/kernel/codegen/.../generator/BackendServiceServerGenerator.java:210-247` (collections: get/put/set/remove/delete/contains_key/get_all/key_set/size/clear/put_if_absent/watch; instance-keyed: set_instance_keyed + reads; singletons `:198-208`), plus watch pollers at `:352-368` (`server_collection_poll`, `server_singleton_poll`) scheduled every 500 ms (`:191`). Each fragment begins with `checkAccess(...)` which reads `SecurityAuthenticator.CALLER_SERVICE_PATH_KEY.get()` from the gRPC Context (`KCG/SecurityAuthenticator.java.template:206-235`), so the caller identity is already in scope at exactly the line where `request.getKey()` is used (`KCG/fragments/server_collection_get.java.template:7`, `server_collection_put.java.template:8`, `server_collection_set.java.template:8`, `server_collection_remove.java.template:7`, `server_collection_delete.java.template:7`, `server_collection_put_if_absent.java.template:8`).

The Context is populated by `callerInterceptor()` installed server-wide at `.../cluster/ClusterServer.java:552` (and again for the JWK view server at `:601-603`). Adding a `CALLER_NAMESPACE_KEY` next to `CALLER_SERVICE_PATH_KEY` at `KCG/SecurityAuthenticator.java.template:328-333` makes the tenant available to every fragment with no further plumbing.

**Entry points that bypass the choke point (deliberately fine):**
- In-process kernel writers use `BackendMap` directly with no Context: `TenantAdminServiceImpl.java:106,256,288,330,610`, `ClusterStatePublisher.java:167,179,243`. These are `/system` writers of `/system` roots; a tenant-owned service would never be granted `rw` on them anyway (policy is per-graph `rw/ro` lists, `SecurityAuthenticator.java.template:221-235`).
- `BackendStoreServiceServer` (`(spec.service_store)`, `KCG/BackendStoreServiceServer.java.template`) is a *second* template with the same shape: one replicated map named `<ValueType>Store` (`:32,46`), key taken from the record's `store_key` field (`:54-63`), `list()` returns all values (`:124-131`), and `GRAPH = NO_POLICY_GRAPH` so `checkAccess` is a no-op (`:34-35,140`). It must get the same rewrite (4 RPCs) — and note it currently has **no authorization at all**, so today any authenticated service can read any store.
- `ViewServer` (`(spec.view_member)` unions, `BackendServiceServerGenerator.java:325-347,370-406`) re-emits source-map `entrySet()` keys — same strip needed.
- Topics/queues: `statemap_topic.java.template`, `server_topic_subscribe*.java.template`, queue fragments — **no key at all**; the Hazelcast object name is fixed per boundary (`BackendMapGenerator.java:65-71`). Isolation there would require per-tenant object names (`name + "/" + tenant`) opened lazily, a different mechanism from key prefixing.
- Leader election RPCs (`server_leader_*`) are per-boundary singletons — same problem as topics.

**Watch/subscription fan-out.** There is no eventbus involvement in kernel state Watch: `server_collection_watch.java.template` sends an initial full snapshot then registers a `WatcherEntry`; `server_collection_poll.java.template:3-8` rebuilds the *entire* `EntriesResponse` from `entrySet()` and sends it to every watcher whose `lastSent` differs. Because each watcher gets the whole map, a per-tenant watcher needs its own filtered+stripped snapshot and its own `lastSent` comparison — the natural change is to store the watcher's namespace in `WatcherEntry` (`KCG/BackendServiceServer.java.template:92-100`) and build the response per-namespace group in the poller. Clients treat the stream as authoritative snapshots: the Rust wrapper `clear()`s and re-inserts from `resp.entries` (`tacplus/pkg/templates/rust/types/statewrapper.rs.tmpl:707-710`); so a stripped snapshot is consumed with no client change.

## 3. Egress rewriting — where the prefix must be stripped

| Response shape | Where keys appear | Strip point |
|---|---|---|
| `Get/ContainsKey/Remove/Put/PutIfAbsent` -> `ValueResponse{value, found}` | no key in response | none; only ingress rewrite of `request.getKey()` |
| `GetAll` / `Watch` -> `EntriesResponse{map<string,T>}` | map keys | `server_collection_get_all.java.template:8-10`, `server_collection_watch.java.template:11-14`, `server_collection_poll.java.template:4-6`: filter `startsWith(prefix)` then `putEntries(key.substring(prefix.length()), v)` |
| `KeySet` -> `KeysResponse{repeated string}` | keys | `server_collection_key_set.java.template:7-8` |
| `Size` | count over whole map | `server_collection_size.java.template:7-8` must count only prefixed keys (currently `Map.size()`) |
| `Clear` | whole map | `server_collection_clear.java.template` must delete only prefixed keys (currently clears every tenant) |
| Views (`GetAll/Watch` over unions) | keys | `BackendServiceServerGenerator.java:332-333,379-382` |
| Store `List` -> `StoreListResponse{repeated T items}` | **no keys; key is inside each item's `store_key` field** | `BackendStoreServiceServer.java.template:124-131` — filter by prefixed map key, return items untouched |
| Singletons | fixed `SINGLETON_KEY` | `server_singleton_get/set/watch/poll` must use `prefix + SINGLETON_KEY` or the singleton is shared cluster-wide |

**Where a naive strip would miss / where paths leak inside payloads:**
- **Key-as-field records.** The client wrapper upserts by the record's `(spec.indexed)` field (`statewrapper.rs.tmpl:278-288`, `add_*` inserts `item.<KeyFieldName>`), and view lookups compare `item.<KeyFieldName> == key` (`:323-328`). This works only if the *stripped* key equals the field. Rule: **prefix the map key only; never touch the payload.** Then the field the service wrote (`"table"`) equals the key it sees back (`"table"`). Do not attempt to rewrite fields.
- **`instance_keyed` composite key** (`server_collection_set_instance_keyed.java.template:31-37`) writes `id = serviceId@instanceId` into the payload. Under a prefix the map key is `/<tenant>/svc@inst` but `id` stays `svc@inst` — consistent with the rule above. Consumers of `ServiceHealth` (`kernel.proto:898-907`) are `/system` services (sentinel), which see the real key; fine.
- **`ProjectConfigEntry.project_namespace` (`kernel.proto:1071-1074`) and TenantAdmin keys** are real namespace paths written by a `/system` writer into a `/system` root. A tenant-owned service is never a writer here; if it were granted `ro` it would see these keys un-stripped (no prefix match) — i.e. **a prefixed reader sees an empty ConfigState**, which is the correct chroot behaviour but may surprise anyone expecting "my tenant's config slice" from a tenant-scoped service. The existing per-tenant config delivery (`tacplus/pkg/internal/proto/configholder.go:1123-1210`, `CONFIG_SLICE_SCOPE_TENANT`) is a separate export mechanism and unaffected.
- **Cross-record references** inside payloads (e.g. `Grant.delegate_name`, `WorkloadRevocation.spiffe_id`, `kernel.proto:936-939`) are SPIFFE IDs / names, not map keys — no rewrite applies and none is needed.
- **`FencedLock.key`** (`kernel.proto:535-537`) is explicitly "opaque to kernel; callers partition the namespace themselves" — a Ratis-backed lock, not a state map. A tenant-owned service could collide with / steal another tenant's lock names unless `FencedLockServiceImpl` gets the same prefix. Out of the state-map generator but same one-liner shape.
- Resource SPIFFE IDs `spiffe://td/<ns>/data/<kind>/<id>` (`spec.proto:1178-1189`, `Spiffe.java.tmpl:490-491` `DATA_SEGMENT`) already carry a full namespace path inside record payloads. These are *record-store* identities and a `/data/...` string in a payload is not a kernel key, so a key-prefix strip neither should nor could touch them.

## 4. Existing precedent

- **Server-authoritative key from Context:** `instance_keyed` (`server_collection_set_instance_keyed.java.template:9-37`) — the only place kernel derives a key from the caller. It is a *write-only* rewrite (reads still take a raw key), so it is half of the pattern.
- **Predicate PIN, not translation:** `(spec.namespace)`/`(spec.store_namespace)` (`spec.proto:1961-2006`; Java `recordnamespace_gen.go:262-290`; Rust `namespace_gen.go:84-108`) live in the *application service wrapper*, over record-plane RPCs. Semantics: the caller may name the tenant, and it must equal the claim; rows stamped with another tenant are dropped-and-abort. This is a pin: the request/record **still carries the tenant as data**. Kernel state has no equivalent at all — kernel `checkAccess` is service-identity-only (`SecurityAuthenticator.java.template:206-254`; policies are `rw/ro` service lists, `SecurityAuthenticatorGenerator.java:23-32`).
- **C2S is already "caller sees only its namespace"?** Only on record-plane and `target_namespace_field` RPCs, and only as PIN/filter (`spec.proto:1358-1369`, `C2SScope` `:2400-2418`). C2S callers do not reach kernel state services at all (`state.go:600-616`: state services are `service_s2s` except the eventbus C2S topic path). So no, there is no C2S precedent for kernel state.
- **Per-tenant topic names / storage prefixes:** none found. Map names are `class:field` (`BackendMapGenerator.java:54-71`); store maps `<Type>Store` (`BackendStoreServerGenerator.java:44`).

**Pin vs. translation, precisely.** With a PIN the service's request contains `namespace="/acme"` (or is stamped to it) and the store is queried with that predicate; the service is tenant-*aware* and the tenant is a field in its data model. With TRANSLATION the request contains only `key="table"`; the kernel computes `"/acme/table"` from the token, and the service's data model has no tenant field. The tenant-owned-service case is therefore **not** "treat the token like C2S with namespace=<tenant>": the pin machinery has nothing to pin (no namespace field on `GetRequest`/`PutRequest`, `state.go:806-812`) and operates in the wrong process (the callee service, not kernel). What must be added is a key-space rewrite in the kernel state servers keyed off a new `caller-namespace` Context value. The two mechanisms compose: pin protects record-plane RPCs a tenant service *serves*; translation protects kernel state a tenant service *consumes*.

## 5. Size and shape

**Kernel codegen only (Java), plus a Context key.** No tacplus generator change is required for the data path: the wire proto (`state.go`) is unchanged, the Rust/Java state clients pass keys through untouched (`statewrapper.rs.tmpl:297-303`) and replace caches from `entries` (`:707-710`). tacplus would only be involved if you wanted a generation-time flag (e.g. `(spec.service_state).tenant_scoped`) to make the rewrite opt-in per root; the simplest v1 is *unconditional*: prefix iff the caller's namespace is not `/system…`.

Concrete code paths (all under `platform/services/kernel/codegen/`):
1. `SecurityAuthenticator.java.template:328-333` — add `CALLER_NAMESPACE_KEY` (value from the token's `namespace` claim; depends on the identity work so `/<tenant>/services/<name>` parses — today `Spiffe.java.tmpl:476-483` classifies SERVICE only under `/system`, and `resolveCallerFromToken` rejects otherwise at `SecurityAuthenticator.java.template:398-408`).
2. A tiny `NamespaceScope` helper (prefix computation, `scopeKey(k)`, `unscopeKey(k)`, `owns(k)`), emitted once like `SecurityAuthenticator`.
3. Collection fragments (11): `server_collection_{get,put,set,remove,delete,contains_key,get_all,key_set,size,clear,put_if_absent}.java.template` — one-line ingress rewrite, or filter+strip on the four that enumerate.
4. `server_collection_set_instance_keyed.java.template:31` — prefix `compositeKey` for the map only.
5. `server_collection_watch.java.template` + `server_collection_poll.java.template` + `WatcherEntry` (`BackendServiceServer.java.template:92-100`) — carry namespace per watcher, build per-namespace snapshots. Same for view watch/poll in `BackendServiceServerGenerator.java:325-406`.
6. Singleton fragments (4): `server_singleton_{get,set,watch,poll}` — `prefix + SINGLETON_KEY`.
7. `BackendStoreServiceServer.java.template` — 4 RPCs (and this server should also get a real policy; it is `NO_POLICY_GRAPH` today, `:34-35`).
8. Topics/queues/leader: **not key-addressable** — needs per-tenant Hazelcast object names in `BackendMapGenerator.java:65-71` or an explicit "tenant-owned services may not use topic/queue boundaries" rule. Recommend the rule for v1.
9. `FencedLockServiceImpl` — optional, same prefix rule on `key`.

Roughly: ~20 template touch points, one generator method for the poller, one new helper. A day or two of work once the Context key exists.

**Reasons it cannot be fully transparent:**
- Topics, queues, leader records and singletons have no caller-chosen key; they need object-name partitioning, not key prefixing (see 8/6).
- Roots whose keys are *semantically* namespaces (`ConfigState`, written by TenantAdmin with `ns` as key, `TenantAdminServiceImpl.java:106,256,288`) are `/system`-owned; a tenant-owned reader with `ro` would see an empty map, by design. Anyone who wanted "the tenant's own config" from such a service must use the config-slice export instead.
- `Size`/`Clear`/`KeySet` change from O(1)/native map ops to prefix scans; acceptable at current `assert_max_size` bounds (≤4096, `kernel.proto:1087-1105`) but it is a behavioural change.
- `Query`/`WatchQuery` are on the wire (`state.go:669-670,832-836`) with no kernel implementation (no match for `QueryRequest`/`CollectionQuery` under `platform/services/kernel/`), so nothing to translate today — but a future implementation with `CollectionQuery` predicates must be written prefix-aware from the start.
- The Hazelcast map is shared across all tenants under one name; isolation is by convention in the kernel code, not by Hazelcast. That is the same trust level as `instance_keyed` today, so acceptable, but it is not "the service can never escape its prefix" at the storage layer — it is "the kernel never lets a non-`/system` caller name an unprefixed key."
