Suggestion: Every service pod runs as non-root by the operator's say-so and the namespace's Pod Security level, not by each Dockerfile's
Type: Security
Summary: Three services the fleets deploy still run as root: gateway (Dockerfile:41, gateway#29), oauth (Dockerfile:31, oauth#22) and messaging (Dockerfile:4, messaging#14), the last two 'new since the previous run' in tonight's security reports; 13 other images declare USER nonroot or 65532. Nothing in the cluster enforces it: the operator renders no securityContext but an fsGroup for pods with a PVC (pkg/helm/generator.go), and no namespace carries a pod-security.kubernetes.io label. Have the operator render runAsNonRoot, runAsUser and runAsGroup 65532, allowPrivilegeEscalation false, capabilities drop ALL and seccomp RuntimeDefault on every service pod, and label the tac-<deployment> and tenant namespaces restricted (audit now, enforce at the first deploy)
Why: The three Dockerfile issues fix three images, and the next image without a USER (redo has no Dockerfile yet, redo#2) starts the cycle again, with a build's security floor the only thing that notices, per repository, per night. Jody's CI containers already run non-root with no privilege and no capabilities (the looper redesign; the control runner's config: privileged false, no escalation, seccomp RuntimeDefault, drop ALL), while the deployed services, the ones a tenant's request reaches, have no such rule anywhere: blobstore's and llmproxy's PROPOSALS asked the operator for it on 2026-11-08 and 2026-11-09 and no operator issue exists. With fleet-seatrials' first deploy on dev (bar B) next, a namespace label makes the rule the cluster's: an image that runs as root is refused at admission, once. Also serves Operability (one setting, platform-wide) and Resiliency (the uid, group and fsGroup agree, which is what the eventbus PVC fix in the operator was about)

## Reuse considered
Kubernetes Pod Security Admission is built in (a namespace label, nothing to install); the operator already renders fsGroup 65532 for PVC pods and 65532 is the fleet's uid (blobstore#18); the control runner's pod settings in cluster are the template for the values. Considered: the per-repository Dockerfile fixes alone (needed and under way, but a Dockerfile is one image's, and a regression passes until the next nightly); Gatekeeper or Kyverno (a new component where the admission controller already does it); enforce from day one (the three root images would be refused at bar B, so audit first)
