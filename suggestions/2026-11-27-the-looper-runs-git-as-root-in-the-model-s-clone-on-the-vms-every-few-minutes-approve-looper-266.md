Suggestion: On the looper VMs the looper runs git as root in the model's clone every few minutes (the checkpoint ticker and the claim heartbeat), the hazard looper#227 closed for scans, now where root holds the container socket: approve looper#266 with that as its fix
Type: Security
Summary: looper#266 (filed 2026-11-27 00:11Z, a bug with no approval) found root-owned loose-object directories and refs appearing in a report's clone on looper-vm-tacplus-dev about every five minutes and at each --build, so the model's own commits and its --land fail 'insufficient permission' (#261, #262: 'could not fetch main; nothing queued'). The objects are the looper's: checkpoint() and claim_take() run git add -A, write-tree, commit-tree, push, fetch, ls-remote and update-ref inside $CHECKOUT, the clone model_user_up chowned to the model's user, as the looper's own user, which on a VM is root, and report_reown() only chowns the results back afterwards. git reads that clone's .git/config and hooks, which the model's user writes: a pre-push hook, core.fsmonitor or credential.helper the model plants runs as root at the next tick, on a VM whose root holds the container socket (decision 2026-11-24, point 5: 'anything the main container runs can read whatever the VM holds'), the VM account's metadata credentials and every report's token. looper#227 (closed 2026-11-25) removed exactly this from the nightly scan ('a scan's model can get a command run as the job's user'), and the suggestion of 2026-11-24 asked for the rule 'in a scan, a report or a land'; the report's checkpoint path still has it, and on a VM it fires every five minutes instead of hourly. Run the ticker's and the claim's git as the report's user (setpriv --reuid, as the model's own --checkpoint already runs this code and pushes), never as the parent, drop report_reown, and approve #266 priority:high with its acceptance test (after a checkpoint no file under .git is root's) and one more: a pre-push hook and a core.fsmonitor the model user plants in the clone run nowhere
Why: The VMs went live on 2026-11-25 and work the agentic flow's own issues (looper#249 to #252, #261, #262), so the clone a model owns and the parent's root git meet many times an hour on the box that holds the socket; the symptom is already a Correctness cost tonight (#262's land queued nothing, #261 worked around it by hand with GIT_OBJECT_DIRECTORY). Also serves Correctness and Operability

## Reuse considered
looper#227's own pattern (the looper copies the files it needs out of the model's clone into a tree of its own and runs git there) fits the scan, which takes PROPOSALS.md once; a checkpoint needs the whole working tree every few minutes, so copying is the wrong size. setpriv to the model's user is what repo-looper already does for the model itself (model_user_up, the setpriv --reuid line), and the model's own --checkpoint already runs this very code as that user and pushes, so the parent doing the same adds no credential and no new tool. #266's workaround (a temporary GIT_OBJECT_DIRECTORY and a pack the user owns) fixes the symptom and leaves root's git in the clone; #254 (no git identity on a VM) and #255 (a failed checkpoint deletes the branch), both in the open suggestion of 2026-11-26, are the same code path and land together
