Suggestion: A land whose base commit published no report compares with its nearest published ancestor on main, or the last nightly's, so a HISTORY.md or PROPOSALS.md push does not fail every land on main's standing findings
Type: Performance
Summary: looper#180 (accepted 2026-11-17) has a land fail only on blocking findings its change adds, by reading its base commit's findings package; but the base is the exact commit the land is built on, and when that is a commit no build published, the loopers' own bookkeeping (the manager's HISTORY.md push after a merge, the nightly scan's PROPOSALS.md push, an agent's ROADMAP edit), every blocking finding fails and every finding is 'new'. Tonight 18 of 31 'latest' reports say 'No findings of the base X (its build published none): every finding failing the policy fails this build', and all 18 bases are such commits (16 HISTORY.md or PROPOSALS.md, 2 ROADMAP.md); gateway's and eventbus's builds failed on one standing finding each (gateway#29's root Dockerfile; CollectionRuntime.java's spotbugs HIGH), gateway's base being the 2026-11-20 nightly scan's PROPOSALS commit for two days; tacplus's reads 9815 'new'. Have looper-scan walk main's first-parent history from the base to the nearest commit with a published package (else security-<repo>/nightly, which looper#211 publishes), say which commit it compared with, and never compare with nothing while main has a report
Why: Each such land is a full build (55 min for tacplus) that ends red for a finding the change did not add, then a send-back and a build again; and a floor that goes red on a bookkeeping push is what pushes rule-wide exceptions, the thing looper#182 and the open suggestion of 2026-11-13 are undoing. Also serves Security (the floor's 'new' means new again) and Correctness (the rule #180 promised holds)
