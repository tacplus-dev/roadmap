Suggestion: The security floor scans the image a release ships, never a builder stage or a Dockerfile nothing builds
Type: Security
Summary: looper-scan's base_images scans every FROM 'by name, not a stage': deploymentproxy's build stage golang:1.27 fails its floor on 7 fixable HIGHs (deploymentproxy#23) while its release image is distroless static nonroot; gateway's and oauth's Dockerfile.cross ('Used for local development builds', built by nothing) fail theirs on rust:trixie's 4 CRITICAL OpenEXR and 30 HIGH libpq findings (2695 each); opa#17 is a Dockerfile.cross running as root. Meanwhile nothing scans what ships: pigeon (GO-2026-6859 and CVE-2026-4738 'found only with a separate trivy image'), doppelganger, coop (the launcher c54ae30 its images run as PID 1 'showed up in no report') and registry (build:2.6.5 'shipped 19 fixed HIGH/CRITICAL CVEs', the report said '0 finding(s)') all ask for it in PROPOSALS of 2026-11-12 to 11-17. Scan only the last stage's base of a Dockerfile the repository builds, and on a release and the nightly the published image itself by digest (trivy image, looper#167's govulncheck -mode=binary on its binaries): PRODUCTION.md's bar is 'shipped images'
Why: Three repositories' floors are red tonight on packages that never ship, and the exceptions that would clear them are rule-wide (the 2026-11-13 suggestion's problem), while the images the fleets will pull carry findings no report has seen: pigeon's and coop's launcher built with go1.27.3 (GO-2026-6859) and with launcher#7's InsecureSkipVerify, registry's build image with 19 fixed HIGH/CRITICAL CVEs. Bar A of 'SeaBeam can start' is release images and the fleets' pins (decisions/seabeam-can-start-2026-11-12.md): the floor should judge those images before a fleet locks them. Also serves Performance: deploymentproxy's, gateway's and oauth's security jobs stop failing on builder packages (3 of tonight's 14 red nightly security jobs), and Operability: no needs-decision issue for packages nobody ships (deploymentproxy#23's 182 advisories).

## Cost
A day or two in looper-scan and looper-build: base_images keeps only the last stage's FROM of each Dockerfile the repository builds (the release Dockerfile its release workflow or tacplus.yaml names; Dockerfile.cross and other unbuilt files listed as 'not built, not scanned'); a release's publish job and the nightly add trivy image of the published image by digest (the archive publish keeps, or ghcr at the tag's digest) and run #167's govulncheck -mode=binary over its binaries, the launcher included; findings keyed 'image <ref>' as today. Tests: a builder-stage HIGH does not fail the run, a HIGH in the release image's base or binaries does. deploymentproxy#23's move to alpine and opa#17 become unnecessary.

## Reuse considered
looper-build already has publish (the release image, its digest and archive image.tar) and sbom of that archive in the looper image, where trivy is: trivy image --input image.tar and govulncheck over its unpacked binaries fit there with no new tool. looper-scan's base_images awk already knows stages (it drops a FROM naming one); keeping only the last FROM is the change. looper#167 built the binary scan for the looper image; the same code runs on a service image. Considered: a per-repository exception for the builder packages (rule-wide today, 182 ids for deploymentproxy alone) and deploymentproxy#23's switch to alpine (quiets one repository, scans nothing that ships).
