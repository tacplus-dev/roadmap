Suggestion: A tenant's pigeons now run as Jobs in the tenant's own namespace with no NetworkPolicy: they share the tenant's services' network and lose their external egress; decide and render their policy before seatrials' first deploy
Type: Security
Summary: Since coop#17 (MODE_JOBS, promoted by Jody via the hub on 2026-11-26 and built the same day) and operator#47 (landed 2026-11-27) a shared coop runs each tenant's pigeons as Jobs in tac-<deployment>-<tid>, beside the tenant's own stratum, blobstore, mailbox and messaging pods. coop's PROPOSALS (2026-11-26) records what that leaves open: coop renders no NetworkPolicy and nothing renders one for pods labelled coop.tacplus.dev/run, so a pigeon, a model-driven job that fetches external domains up to its kind's domain_ceiling, 'now shares the namespace, and its intra-namespace egress, with the tenant's own services, where the old pigeons namespace held nothing else'; and the namespace's egress (deploymentproxy's) 'stops at the namespace, DNS and tac-<deployment>', so a pigeon's external fetch is cut off unless it goes out through an egress proxy in tac-<deployment> (coop's slice 3, not built); pigeons also count against the tenant's quota, and a Job the quota refuses ends the run FAILED. 'Not observed on a live fleet yet': seatrials, the top goal, is the first, and the only policy the cluster keeps today is kernel-raft (operator#24 removed the rest). Decide the pigeons' network now and file it approved on operator and coop: a NetworkPolicy the operator renders with the tenant namespace for coop.tacplus.dev/run pods (egress to DNS and the deployment's egress proxy only, no ingress, nothing else in the namespace), the proxy itself, and a fleet-dev e2e leg that a pigeon cannot open a tenant service's port while its allowed fetch succeeds. fleet-seatrials#83 holds only the config key
Why: Pigeons are the first workload that runs a model's choices inside a tenant namespace, next to the tenant's data services, and the move put them there two days before seatrials deploys; the tenant-isolation rule (s2s never crosses tenants; the record plane's tenant checks) assumes the namespace holds the tenant's services alone. Also serves Correctness: today every pigeon's external fetch fails at the namespace fence, so the feature ships broken on the first fleet

## Cost
A few days: the operator renders the NetworkPolicy beside each tenant namespace (deploymentproxy applies what the operator renders there, as the namespace itself), keyed by the coop.tacplus.dev/run label coop already puts on every pigeon pod; the egress proxy in tac-<deployment> is coop's own slice 3, sized by its design (a forward proxy that enforces domain_ceiling is the same check coop makes today, moved to the network); fleet-dev#3 gets the e2e leg. A decision from Jody only on the shape (a policy per tenant namespace rendered by the operator, as kernel-raft is); nothing to buy

## Reuse considered
The operator already renders per-tenant namespaces and the one NetworkPolicy the cluster keeps (kernel-raft, operator#24's exception), so a second policy selected by the coop.tacplus.dev/run label is a template beside it, not a new mechanism; deploymentproxy's namespace egress rule is the fence that cuts the pigeons off today and stays as the default; coop's 'egress through a proxy' slice is the design its proposal names for the external fetch, and domain_ceiling is the rule the proxy enforces. The old pigeons namespace (pigeons_namespace, kept for the empty map) is the fallback if the policy is not ready before seatrials deploys: a decision, not code
