Suggestion: A deleted tenant's user and session tokens do not mint in a new tenant of the same name, and a proof's jti is refused on reuse across kernel nodes
Type: Security
Summary: kernel's PROPOSALS, open since 2026-10-27: DeleteTenant refuses every mint into the deleted tenant, 'but the refusal ends when a tenant of the same name is created': user and session tokens, grants and delegates name the tenant by name, not tid, so 'a refresh token (24h) or offline token (90 days) issued in the old tenant would then mint in the new one' (#23 closed the service-token half only). And seenProofJtis is per kernel node, so a captured client-minted proof 'can be replayed once per other node inside its window' (300 s for workload keys). Neither has an issue. Refuse a token whose iat predates its namespace's latest tombstone (TenantIdRow.tombstoned_at_ms is already there), and keep the proof replay set cluster-wide
Why: The tenant-deletion decision says deletion is destructive and complete and the platform ROADMAP lists kernel#19 as done, yet a 90-day offline token outlives its tenant and reaches the namesake that replaces it: tenant isolation (s2s-never-crosses-tenants, tenant-routing) rests on a name here. The decision's table says issued tokens are not chased because ATs and STs are short-lived, which refresh and offline tokens are not. Both are kernel-only fixes with the data in place, cheaper before any fleet is deployed (bar B) than after, and bugs under the issue flow: fix, then a 0.1 patch. Also serves Correctness: the decision's words become true for the long-lived tokens too

## Reuse considered
TenantIdRow.tombstoned_at_ms is stored per tid already (kernel#3), so the refusal is a comparison at mint; #23's tid-in-the-subject is the model for the larger change; Hazelcast is kernel's cluster store already (its port in the accepted 2026-11-10 suggestion) and gives TTL maps, the FencedLock the PROPOSALS' other option. Considered: chasing issued tokens at deletion (the decision says no; this refuses them when used instead); shorter offline tokens (a product choice, and 24 h refresh tokens have the same hole); leaving it to the identity-graph work (items/identity-graph.md: later, and about people, not tenant namespaces)
