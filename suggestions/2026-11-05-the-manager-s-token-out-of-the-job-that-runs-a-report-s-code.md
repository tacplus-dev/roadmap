Suggestion: The manager's token out of the job that runs a report's code
Type: Security
Summary: Until a repository's gates run as build jobs, split its manager: the gates and any regeneration of a batch run in a job of the report's environment, and only a merge step that runs no repository code holds the id_token that mints tacplus-manager, the ruleset's one bypass
Why: looper#83 (closed 2026-11-04) makes tacplus-manager the only identity besides Jody that can update main, so that a model cannot push untested code there. But the manager still runs every report's commits (its tests, its gates, --gates CMD) in its own job, as the job's user, and that job keeps its GitLab id_token for its whole life so looper-token can mint the manager's token again every 45 minutes. A test that a model wrote, maybe on an instruction injected from outside the org (looper#40), runs beside that id_token and can mint the bypass token itself. The README says as much ('What it is not'). Last night the managers merged 22 branches this way across 6 repositories. Gates move into credential-less build jobs (#71) only for a pinned repository, and only looper is pinned. The merge train that would build each batch in a build job (#86) is blocked on #84, which is blocked on tacplus#315. So once Jody installs the apps, the ruleset's guarantee is hollow for every repository but looper. This is best fixed before that setup goes live. Also serves Correctness: the recap's manager score (red main, reverts) assumes the manager is the only writer.

## Cost
About a day in looper-dispatch and repo-looper. The plan gives a repository with no build.lock two jobs for a batch. The first, looper-<repo>-verdict in environment looper-report, merges the queue onto staging, regenerates generated.yaml's files, runs the gates and pushes staging with the report app's token. The second, looper-<repo>-manager in environment looper-manager (needs: the first), checks that staging is the commit the verdict named, fast-forwards main, and posts the verdicts and HISTORY lines. It runs nothing from the repository. KMS's bindings already keep the manager key from looper-report jobs. Tests: a gate that tries looper-token mint manager in the verdict job is refused; the merge job runs no repository script; a staging moved after the verdict is refused. A pinned repository keeps #71's build job, and the split goes away for each repository as it is pinned.

## Reuse considered
Considered first: (1) #71's build jobs already run gates with no forge credential, but only for pinned repositories (one of 31). Pinning the others needs per-repository pin issues the hub has not filed, plus BUILD_TRIGGER_TOKEN. That is the end state, and the split is the bridge to it. (2) #86's merge train builds the batch in a build job, the same shape, but it is blocked two levels deep (#84, tacplus#315). (3) PROPOSALS' 'gates as a user of their own' is cheaper on paper, but the gates need docker (the broker for one more user) and tacplus's tests write caches as root (#69's failures). A job boundary needs neither. (4) #28's think/commit split is this pattern for kernel's pilot; the verdict/merge split reuses its idea with GitLab environments and needs: rather than a new identity. (5) The 'Require the build's status on main' proposal would refuse an unbuilt push, but only once every repository builds in tacplus-dev/build.
