Suggestion: A SAST exception accepts one finding where it is, not its rule everywhere in the repository
Type: Security
Summary: looper-scan gives a SAST finding the bare rule as its id (gosec 'G703', alias 'CWE-22'), and an exception matches on id or alias alone, never on where. So accepting one false positive, as tonight's needs-decision issues ask (tacplus#572, #577, opa#15), accepts that rule anywhere in the repository, in every later commit, until it expires. Match a SAST exception on tool, rule and path, and refuse one that names no path
Why: Tonight's nightly scans filed about 20 per-finding gosec and semgrep issues in tacplus (#565 to #584) and opa#15. Several are needs-decision, which hands Jody the choice to accept: e.g. tacplus#572 (G702, CWE-78) at cmd/sitegen/annotations.go:99, a dev tool running the protoc that PROTOC_BINARY names. An exception is the floor's only way to accept a finding (no repository has security-exceptions.yaml yet, so the first entries will be written for these). As written, an entry 'id: G702' would accept command injection in every Go file of tacplus. 'id: CWE-78' would also cover bandit's findings, whose aliases are CWEs too. The same goes for launcher's G402 (InsecureSkipVerify on its localhost health probe, main.go:125): accepting it accepts any later InsecureSkipVerify toward a remote peer. The floor (looper#49) is supposed to fail on 'a HIGH SAST finding in our own code unless an exception names it'. A rule-wide exception names nothing, and the 'new since the previous run' list doesn't help: a matching finding is marked excepted and never blocks. Yesterday's gitleaks suggestion is the opposite flaw, an id too narrow to survive a moved line. This one is an id too broad to say what was accepted. Also serves Correctness: the summary's 'accepted by an exception' would mean what it says

## Cost
Hours to a day in looper-scan, by a looper. read_exceptions takes an optional 'where' (a path, or path:line). In scan_tree, a sast or config finding is accepted only by an entry whose tool, id and path match its own. An sca finding keeps matching by id or alias, since its aliases are CVE and GHSA ids that do mean one advisory. An exception for a SAST rule with no where becomes a problem that fails the run, as one with no reason does today. Tests in tests/looper-scan.test.sh: an exception for G703 at a.go does not accept G703 at b.go, and a CWE alias accepts no SAST finding. The README's Security checks section says how to write one. Nothing to migrate: no repository has a security-exceptions.yaml yet

## Touches
looper#49 (the deterministic floor: a HIGH SAST finding fails unless an exception names it), decisions/throughput-first-2026-11-11.md (security findings first; the hub approves them), looper#129 (one issue per cause: a cause can still be accepted path by path), the open suggestion of 2026-11-12 on gitleaks ids (the same exception file, the opposite flaw), tacplus#565-#584 and opa#15 (tonight's decisions that would write the first entries)

## Reuse considered
The exception file, its parser and its expiry checks exist, and only the match changes. Considered: (1) per-line '#nosec G703 -- reason' annotations in the code. gosec honours them, but they put the decision in the diff a report writes, not in a file the hub reviews, and they need a decision per tool (semgrep has nosemgrep, bandit '# nosec'). (2) Putting the path into the SAST id, as gitleaks does. That breaks every 'new' comparison once, and it is what the open gitleaks suggestion moves away from for lines; matching on where keeps ids stable. (3) A per-repository gosec config excluding a rule. That is coarser still, the same flaw by another route
