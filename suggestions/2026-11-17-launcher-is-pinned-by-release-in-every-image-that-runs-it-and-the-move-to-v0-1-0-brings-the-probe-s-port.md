Suggestion: launcher is pinned by release in every image that runs it, and the move to v0.1.0 brings the probe's port
Type: Security
Summary: Six service images run tacplus-dev/launcher as PID 1, pinned six ways, five of them before launcher#7's fix (G402: the health probe's InsecureSkipVerify) and its go1.27.4 toolchain (GO-2026-6859): coop's and pigeon's release.yml build c54ae30 (coop#14, pigeon#12), tenantecho's d130eab (2026-10-27, no issue), and fleet-seatrials' images/pins.yaml gives eventbus and stratum launcher_commit c575e14 (2026-10-24), 'whose go.mod has the vulnerable grpc v1.81.1 / x/net v0.51.0' (launcher STATE.md). Only kernel pins the release (LAUNCHER_VERSION=v0.1.0, ADD --checksum). None of the five can take v0.1.0 as is: their Dockerfiles set HEALTH_PORT=8443, the TLS port, with no HEALTH_CA, which a post-#7 launcher probes in plaintext, 'fails on a TLS port and kills the child after HEALTH_TIMEOUT'. Pin launcher by release (kernel's pattern in every release.yml, a launcher line the fleet lock resolves), move all five to v0.1.0 in one change with HEALTH_PORT=8444 or HEALTH_CA, and let the release's scan read the launcher binary (suggestion 1)
Why: A fix the floor demanded in launcher (#7, closed 2026-11-15, released v0.1.0) reached one of six images; the other five ship a probe that skips certificate verification and a grpc and x/net with known advisories, and no report says so because the binary is built from source in each release workflow and scanned nowhere (coop's PROPOSALS, 2026-11-17). The platform pins everything else by release line and digest (decisions/deterministic-builds-2026-10-27.md; the fleets pin MAJOR.MINOR), but a binary six images embed is pinned by six commits in six files. Bar A (release images and pins) will lock these images as they are. Also serves Resiliency: taking v0.1.0 without the port change kills eventbus and stratum at their first probe, a trap launcher's PROPOSALS described on 2026-11-09 with no issue, and pigeon#12 is about to walk into.

## Cost
Hours per image, as one coordinated change: coop's, pigeon's and tenantecho's release.yml take LAUNCHER_VERSION=v0.1.0 with the release asset's checksum, as kernel's Dockerfile does, and their Dockerfiles HEALTH_PORT=8444 (the chassis health_probe_port) or HEALTH_CA and HEALTH_SERVER_NAME; fleet-seatrials' images/pins.yaml launcher_commit becomes the release (images/build.sh fetches the asset), and eventbus's and stratum's Dockerfiles move the port in the same patch; Jody decides coop#14's question (plaintext 8444, or TLS with HEALTH_CA) once for all six. Later: a launcher line in fleet.yaml the lock resolves by digest, so the next launcher patch moves every image by one pin.

## Reuse considered
kernel's Dockerfile already pins the release asset by version and checksum: copy it. The fleet lock (tacplus fleet build, tacplus#180) resolves lines to digests for services; a launcher line is one more entry. coop#14's needs-decision question is the port decision asked for one repository: decide it for all six. launcher's release.sh reproduces the assets bit for bit (launcher PROPOSALS, 2026-11-15), so the checksum pin is stable. Considered: leaving each repository's issue to move its own pin (pigeon#12 does, without the port, and would kill its pod; tenantecho, eventbus and stratum have no issue at all).
