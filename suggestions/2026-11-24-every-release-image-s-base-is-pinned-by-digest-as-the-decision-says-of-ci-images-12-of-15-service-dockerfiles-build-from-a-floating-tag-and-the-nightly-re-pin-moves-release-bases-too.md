Suggestion: Every release image's base is pinned by digest, as the decision says of CI images: 12 of 15 service Dockerfiles build FROM a floating tag, and the nightly re-pin moves release bases too
Type: Security
Summary: Jody's decision of 2026-11-23 (point 2) says 'Repositories pin immutable tags only (dated or patch), never a floating one', and looper#226's nightly maintenance re-pins the CI images; but the images the fleets deploy are built FROM floating tags (read 2026-11-24): redo and oauth debian:trixie-slim (Dockerfile:10, :6), opa, coop, pigeon, tenantecho, doppelganger and blobstore alpine:3.24 (:6, :13, :6, :7, :7, :6), mailbox and messaging gcr.io/distroless/cc-debian13 (:2), deploymentproxy's release stage gcr.io/distroless/static-debian13:nonroot (:17, while its build stage is by digest), eventbus busybox and gcr.io/distroless/java21-debian13 (:6, :9; stratum's java21 too). Only gateway, llmproxy and kernel pin by digest, and no release.yml passes a BASE_IMAGE build-arg, so the default is what a release builds. redo's PROPOSALS (2026-11-23, #15) says it: 'each build takes whatever the tag is that day, and the tag lags Debian's security fixes (gateway#38, llmproxy#62: zlib1g CVE-2026-85091)'. So a release's content depends on the day it is built, two builds of one tag differ, and the digest the security report scanned (looper#180's base, by name) is not the one shipped. Pin each base by digest now (gateway's form: a digest and apt-get upgrade; tests/release.rs requiring one, as redo proposes), have looper#226's nightly maintenance move a Dockerfile's base digest to its tag's newest beside the CI-image pins, one land a repository, and have the nightly scan file an unpinned FROM in a Dockerfile a release builds as a bug. stratum#40 and eventbus#31 (open) already hold the two distroless java21 pins
Why: Security (supply chain): a floating base is an unreviewed input to every image seatrials' first deploy will run (fleet-seatrials builds its 13 service images from these Dockerfiles on Cloud Build), and whoever moves the upstream tag changes what ships with no commit here; the accepted suggestion of 2026-11-21 (a pin follows its line by a relock the loopers land) and looper#226 settled this for the build images and left the release images out. Also Correctness: decisions/deterministic-builds-2026-10-27.md asks that a build's inputs be pinned, and the open suggestion of 2026-11-17 (scan the image a release ships) only pays off when the shipped digest is fixed
