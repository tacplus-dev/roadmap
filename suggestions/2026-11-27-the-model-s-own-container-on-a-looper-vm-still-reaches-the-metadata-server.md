Suggestion: On a looper VM the model's own container still reaches the metadata server: model-written code can mint the VM account's tokens, sign as the tacplus-looper App and read looper-model-token; cloud's proposal of 2026-11-26 names the fix and no issue holds it
Type: Security
Summary: cloud#111 (merged 2026-11-26) cuts the build containers off from 169.254.169.254 with a DOCKER-USER rule, as the panel's finding 5 asked ('build containers there must not reach the VM's metadata server'); but the report's model runs in the main container, on the host's network, and looper-vm.sh says so itself: 'the main container, on the host's network, still reaches it'. So model-written code the model runs directly (a test, a build script, a cargo build.rs, a go generate) can fetch the VM account's token and do what that account does: sign through KMS as the tacplus-looper App, which pushes looper/* branches, comments and labels on every repository of the org, and read the model's static credential looper-model-token. cloud's PROPOSALS (2026-11-26, from #111) names the change: the model's process in its own network namespace, or a metadata proxy that serves only what the looper's parent needs (the model token's read and the App key's signing); no issue holds it. File it approved on cloud (looper-vm.sh) and looper (the model's process), with a test on the VM that curl to the metadata server fails from the model's user and from a build container, and the parent still fetches its token and signs
Why: The VMs are live and work every repository's issues, whose text comes from outside the org (looper#40); the decision of 2026-11-24 accepted the VM's trust level for the socket knowingly, and the panel of 2026-11-25 then set the one bar it did set, the metadata server, which the model's own process, the larger surface, still crosses. Also serves Operability: the decision's point 11 ('short-lived tokens to VMs based on their cloud identity') starts from a VM whose account only the parent can use

## Cost
A day or two: looper-vm.sh runs the main container off the host's network (a bridge network, where the same DOCKER-USER rule already applies, with the socket mounted by path as now) and the parent reaches the metadata server by an allowed path of its own, or the model's setpriv'd process is started in its own network namespace (unshare -n with a veth, or a slirp) while the parent keeps the host's; or a small metadata proxy on the VM that answers the parent's two calls and nothing else. A test on a VM: curl 169.254.169.254 fails as the model's user and from a build container, the parent's token fetch and KMS signing work. Nothing to buy

## Reuse considered
The DOCKER-USER rule of cloud#111 is the mechanism and already covers every container not on the host's network, so taking --network host off the main container reuses it with no new code; what the parent needs from the host's network is the metadata server alone, which an allow rule for the parent's container gives. The metadata proxy is the other option the proposal names, more code but exact. The report's own token and the model's token stay where they are: this closes the path to the VM's account, not to the model's own credential
