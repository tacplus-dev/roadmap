Suggestion: No git runs as the job's user in a checkout the scan's model owns: approve looper#227 priority:high, so a scan's model cannot get a command run with the manager's token
Type: Security
Summary: looper#227 (filed 2026-11-23T23:48Z by #226's run; a bug with no approval and no comment) says: after the nightly scan's model has run, the looper, as the job's user (root), runs git in the checkout model_user_up chowned to the model's user (looper#83): scan()'s diff of PROPOSALS.md, land()'s worktree add, commit and push in a worktree of that same checkout, drop_worktree and worktree prune, and the end-of-scan checkout -f and clean. safe.directory=* lets git open it, and each call reads config and hooks the model's user can write (core.fsmonitor, core.hooksPath, a pre-commit hook, credential.helper, diff.external, include.path), 'So a scan's model can get a command run as the job's user. That user holds the manager's token, the Docker socket and GITLAB_TOKEN. This defeats the separation looper#68 and looper#83 set up.' Approve #227 priority:high with its recommended fix (no git in the model-owned checkout: read PROPOSALS.md as a file and diff it against git show from a copy the job owns, land from a clone made before the model as maint_prepare does, rm -rf the checkout instead of resetting it), its acceptance test (a pre-commit hook and core.fsmonitor the model plants run nowhere, and PROPOSALS.md still lands), and the rule written in README: the job's user never runs git, or anything else that reads configuration, in a tree another user owns, in a scan, a report or a land
Why: Security first: the nightly scan reads every public repository's issues, PROPOSALS and source, text people outside the org can write (looper#40), and runs on 31 repositories a night; one injected instruction that gets its model to write .git/config or a hook reaches the manager's token, which is the one bypass actor of every main ruleset (looper#83), so it could push to any main. The hole is known, its fix is designed and half-built (#226's own maintenance commit already runs in a clone made before the model), and the issue has sat unapproved since it was filed. Also Correctness: the accepted suggestions of 2026-11-03 (each model as its own user) and 2026-11-05 (the manager's token out of the job that runs a report's code) promise this separation, and the record should be true

## Cost
About a day in repo-looper: scan() reads the model's PROPOSALS.md as a file and diffs it against git show $base:PROPOSALS.md in a job-owned copy; land() in a scan runs in a clone made before the model (maint_prepare's pattern) or a fresh clone from origin; the end of a scan removes the checkout instead of resetting it; a test in tests/repo-looper.test.sh plants a pre-commit hook and core.fsmonitor as the model and shows neither runs. Minutes for the hub: approve and label priority:high

## Touches
looper#68 and looper#83 (each model as its own user), looper#40 (prompt provenance), decisions/looper-identity-panel-2026-10-29 (an identity per role, out of the model's reach), the accepted suggestions of 2026-11-03 and 2026-11-05 (the manager's token out of the job that runs a report's code), looper#83's ruleset (the manager App is its bypass actor, so the manager's token is the key to every main), PRODUCTION.md's security bar

## Reuse considered
#226's maint_prepare already makes a clone before the model runs and reads the model's diff with -c core.fsmonitor=false --no-ext-diff --no-textconv; the same clone can carry a scan's PROPOSALS.md land. The weaker option #227 names (-c core.hooksPath=/dev/null -c core.fsmonitor=false -c credential.helper= on every call) does not close include.path and the keys git adds later, and GIT_CONFIG_NOSYSTEM or GIT_CONFIG_GLOBAL do not cover the repository's own .git/config, so a tree the job owns is the only full answer. looper#73's retirement of looper-docker does not touch this: git, not Docker, is the path
