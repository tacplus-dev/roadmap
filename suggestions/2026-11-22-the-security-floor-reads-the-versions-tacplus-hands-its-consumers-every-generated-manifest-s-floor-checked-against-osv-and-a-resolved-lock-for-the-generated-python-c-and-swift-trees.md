Suggestion: The security floor reads the versions tacplus hands its consumers: every generated manifest's floor checked against OSV, and a resolved lock for the generated Python, C# and Swift trees
Type: Security
Summary: Four nights of scans found advisories in the floors the generated manifests declare (tacplus#264, #309, #312, #338), each by a model querying OSV by hand: a lockfile resolve picks the newest compatible release, so cargo audit, npm audit and OSV-Scanner pass on tacplus's own tree while a consumer that pins the floor gets the vulnerable version (PROPOSALS 2026-11-06, 'No scanner sees them'). And 'just generated' gives the build's OSV-Scanner locks for Go, Rust, Java and TypeScript only: the generated Python tree has no requirements lock (Bandit reads its sources), and the C# and Swift trees are not generated at all, so no deterministic check sees what a Python, C# or Swift client resolves to (PROPOSALS 2026-11-18, #854). Add a gate that generates the cross-test models, collects every declared floor (Cargo.toml, package.json, pyproject.toml, the Go and Java inventory) and fails on an advisory at the floor itself, with OSV's database fetched at run time as govulncheck's is; and have 'just generated' write a requirements.lock, a packages.lock.json and a Package.resolved for one set, so the build's OSV-Scanner reads all three
Why: tacplus is what SeaBeam builds on (the bar, 2026-11-12), and a consumer takes the floors and the resolved versions tacplus emits, not tacplus's own tree: today the floor finds those only when the nightly's model thinks to look, once a night, after release. Tonight's tacplus report lists 11063 findings and no Python, C# or Swift package among them. Also serves Developer experience (a consumer's first audit is clean)

## Reuse considered
tacplus#376's 'generated' recipe and the build's OSV-Scanner already scan four languages' locks: this extends the recipe to the three languages it leaves out and adds the floor pass over dependencies.yaml's inventory, which #338 made the single place a floor moves. The nightly scan's by-hand OSV queries do this today, once a night, by a model, only on what it thinks of; the advisory issues it files (items/tacplus-security-sweep.md) are its output, not a check. osv-scanner has no floor mode (it reads resolved locks), so the floor pass is a small script against OSV's batch API, like the one the scan's model runs by hand
