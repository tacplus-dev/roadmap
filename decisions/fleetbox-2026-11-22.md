# Fleetbox: a whole fleet in one container (2026-11-22)

**Status:** decided (Jody, 2026-11-08 direction; 2026-11-22 "we should create a repo for it. it will have to be part of a
fleet build when enabled"). Open points below carry the hub's recommendation and are decided unless Jody says otherwise.

## What
One container that runs every service of a fleet — kernel, gateway, eventbus, oauth, stratum and the rest — as separate
processes under a small supervisor. The same release binaries a cluster runs, and a real kernel (one Hazelcast member),
not a re-implementation. Repository: tacplus-dev/fleetbox (Rust, Apache-2.0).

## Why (Jody, 2026-11-08)
- It scales to a real fleet: container → compose → cluster with the same binaries and the same kernel. A single-process
  fleet with an embedded kernel is a dead end.
- It is a test harness for any service with fleet dependencies, without a full deployment.

## How
- **Supervisor** (`fleetbox`, PID 1): reads a manifest the fleet build writes (each service: binary, args, ports,
  readiness check, start order from the fleet's dependencies), starts the kernel first and waits for it to be ready, then
  the rest in order; forwards signals; prefixes each process's logs with its name; exits non-zero if the kernel dies.
- **Fleet build:** `fleet.yaml` gains an opt-in (`box: true`). When it is on, the fleet build also produces the fleetbox
  image for the fleet's lock: the services' release binaries copied from their release images by digest, a Java runtime
  for the Java services, the generated manifest. Off by default; nothing changes for fleets that don't enable it.
- **Same rules as a cluster:** server TLS plus kernel tokens (no mTLS), real auth on, deployment config from the
  uni-config (operator#17) rendered per process by the supervisor — no operator and no Kubernetes inside the box.

## Open points, with the hub's recommendation (decided unless Jody overrides)
1. Crash policy: restart a crashed service with backoff; the box reports unhealthy after repeated failures. A
   `--fail-fast` mode for tests exits on the first crash.
2. Architecture: arm64 first (the cluster is Axion; Jody's Macs are arm64), amd64 after.
3. Port: only the gateway's port is exposed; services talk inside the container.

## Later
- The test fixture: one box per test run, per-test tenant/project isolation, the service under test joining as an
  external member with kernel-issued credentials; generated per server language by tacplus.
- Native host members (hardware or desktop apps that can't live in a Linux container) joining the box as external members.

## Not doing
- A single-process fleet or an embedded/fake kernel.
- Putting it on the seatrials critical path: seatrials keeps deploying to the cluster. Fleetbox runs in parallel.
