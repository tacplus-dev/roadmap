1. **“Nothing is queued” is false.** Unlimited children move queues into CPU scheduling, memory pressure, cache locks and model quotas. Assuming each build uses four cores for 30–80 minutes, 50 MRs require **100–267 core-hours/day**, before retries. The eight-core VM supplies 192: **52–139% utilization** for one attempt; two attempts mean **104–278%**. Nine other projects share four cores. Set resource budgets, explicit admission queues and automatic capacity thresholds.

2. **The merger creates head-of-line blocking.** At 50 MRs/day, 10% conflicting and 80 minutes per resolution build consume **400 minutes/day** of serial merger time; 20% consume **800 minutes**. During an eight-hour arrival window, those are **83% and 167% utilization**, excluding agent reasoning. “Only that MR waits” contradicts taking MRs one at a time. Park conflicts and continue merging independent work; fence every eventual resolution against subsequent main changes.

3. **Rolling-check feedback takes up to two builds before diagnosis starts.** A merge just after a check snapshots main waits almost one build before being included, then another for its verdict: **60–160 minutes**, not 30–80. At 50 merges over eight hours, an 80-minute snapshot interval contains about nine merges. Four binary-search builds plus detection and revert verification can total **7 × 80 = 560 minutes**. This assumes deterministic failures and serial diagnosis; interaction failures can defeat bisection entirely.

4. **Parallel gates require parallel capacity.** Nineteen groups finish in the slowest group’s time only with sufficient CPU, memory and I/O. Ten continuously active projects need ten full-suite-equivalent allocations, potentially **190 simultaneous group jobs**. With six equivalent allocations, demand exceeds capacity by **67%**; average snapshot cadence cannot beat approximately **10T/6**, before releases or diagnosis. Reserve rolling-check and release capacity separately and measure actual resource consumption.

5. **Release and deployment scheduling impose additional queues.** Nightly publication adds **12 hours average, almost 24 hours maximum**, assuming uniformly arriving green changes. An on-demand button merely transfers scheduling responsibility. A serialized deployment taking D minutes supports at most **60/D deployments/hour**; a 30-minute rollout cannot keep up with 6.25 hourly merges if every merge triggers publication. Coalesce pending dev releases, preserve explicit production selections, and define freshness targets.

6. **Other waits have no budget.** A kicker polling every P minutes adds P/2 average latency before the stated three-minute boot. Spot capacity shortages have no three-minute bound. Model quotas, forge limits, dependency downloads and cache contention limit throughput. Feature approval, production authorization and capacity approval are human queues. Specify deadlines, escalation owners and queue-age metrics; “agent” and “pipeline” are not latency guarantees.

7. **A green build does not guarantee a safe deployment.** Tests can miss behavioral errors, migrations, authorization failures and incompatible service combinations. An attested bad artifact remains bad. Specify what canary checks, how long it observes, who owns inconclusive results, and which changes cannot be rolled back. Reverting Git or restoring an image does not undo a destructive migration or external side effect.

8. **Q1 — Use an isolated merger with forge-enforced permissions.** Agree with the author’s (c)+(b), provided build VMs cannot assert the trusted acceptance status or obtain main-writing credentials. Otherwise forge-mediated merging launders the same compromised authority. Conflict builds must execute outside the privileged merger. The shared org VM also makes credential compromise an org-wide risk, not merely one project’s risk.

9. **Q2 — Permit clean merges without full rebuilds only inside a bounded unverified window.** Add fast integration checks against the exact proposed merge commit, with atomic base validation; stop admission when rolling checks are red, missing or too old. Disagree with unconditional immediate merging: textual compatibility is not semantic compatibility, and unlimited landing creates unlimited repair exposure. This introduces an intentional, measurable safety queue.

10. **Q3 — Run rolling checks on independently controlled, reserved runners.** Use dedicated heavy-project capacity within that pool and separate caches from untrusted workers. The reason is predictable verdict latency and trustworthy execution, not whether the machine is called a pipeline runner or VM.

11. **Q4 — Make recovery a bounded state machine, not an open-ended agent task.** Stop merges; reproduce the failing SHA once and compare the last green SHA under identical dependencies. Infrastructure failure or inconsistent results go to a named reliability owner. Deterministic failures get a time-limited diagnosis and a verified revert candidate. Conflicting reverts or dependent changes go to one designated repair looper. Never automatically retry the original issue before recovery completes. Disagree that bisecting always identifies one culpable merge: non-monotonic failures and interacting changes invalidate that assumption.

12. **Q5 — Treat worker evidence as feedback; independently produce release authority.** Record exact commit/tree, base, gate-policy version, build-image digest, dependency identities, commands, results and logs. A signature from a VM controlled through its container socket proves origin, not truth. Require protected, independent release execution with provenance binding the tested output to the published digest; sampling cannot establish safety for an unsampled release.

13. **Q6 — Scope through dependency relationships, defaulting unknown impact to full gates.** Include generator-to-generated-language relationships, shared runtime dependencies, fixtures and build configuration. Compare scoped decisions against full runs and measure misses. Protect gate-policy changes separately. Disagree that a bad map is necessarily caught “within one build”: detection takes up to two, and edited or inadequate tests may never detect it.

14. **Q7 — Publish and promote an immutable compatibility manifest across repositories.** Pin exact tacplus versions/digests and test affected consumers before promotion; use backward-compatible staged changes where coordinated deployment is impossible. “Latest patch of MAJOR.MINOR” permits inputs to change between validation and release and creates a hidden upstream release dependency.

15. **Q8 — Run panel reviewers concurrently with bounded capacity and deadlines.** Use one adjudicator for disagreements; timeout means unavailable, not approval. If each MR requires V reviewers taking R minutes, 50 MRs require **50VR reviewer-minutes/day**. Three ten-minute reviews consume **25 reviewer-hours/day**. Define quota allocation and maximum review age before enabling a mandatory panel.

16. **Q9 — Give every durable transition an owner and watchdog.** Cover abandoned reports, failed checkpoints, merger crashes, missing checks, failed releases and stuck deployments. Persist idempotency keys and fenced claims so restarts cannot duplicate merges, reverts or deployments. A failed release has waiting consumers and needs an owner; “Nobody” conceals the outage.

17. **Missing: commit eligibility and control-plane recovery.** Define how release branches obtain green status when rolling checks track main; bind approval to exact commits and artifacts; prevent overlapping pipelines from deploying an older result last. Protect pipeline definitions and credentials from candidate code. Shadow-test recovery and retain an independently deployable known-good controller before retiring the existing path.

18. **First: establish deployment authority.** Isolate credentials, protect policy and require independently tested immutable artifacts plus explicit production authorization.

19. **Second: replace unlimited concurrency with measured capacity and visible queues.** Reserve verification/recovery resources, park conflicts, and publish queue-age and feedback-latency targets.

20. **Third: prove bounded recovery before enabling unrestricted landing.** Exercise flakes, interaction failures, dependent reverts, preemption and stale deployment races; enforce the unverified-main limit.
