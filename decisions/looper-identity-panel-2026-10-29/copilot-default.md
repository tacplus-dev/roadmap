## Findings

- **[severity: blocker] "Protected refs" is a condition on the job's ref, not on the code the job runs, so anyone who can push to a protected branch of the project owns the key.** The design binds KMS `signerVerifier` to `attribute.project_path` and "protected refs" (§2). The looper is an autonomous agent with write access to its own project, so it can edit `.gitlab-ci.yml` or the scripts the job runs and then run them on a protected ref. This works if main is writable by the looper, which it is: it commits to main via the API (§2). It can also leave the job's intended steps out of the pipeline. Today's flow already lets the looper change the pipeline that holds its credentials. Fix: pin the pipeline definition outside the project, using `include:project` from a locked, separately owned project, or a `ci_config_ref_uri` / `job_workflow_ref` claim. Make main in each project require merge requests reviewed by someone other than the looper, and give the looper no Maintainer-level rights.

- **[severity: blocker] The looper's own GitLab token (§3) is a project access token that can edit its own variables and settings, and it can probably edit protections.** An access token with `api` scope and Maintainer role can unprotect branches, add pipeline triggers, change CI/CD variables, and add runners. The design lists "its own variables" as an intended permission. Attack: the looper unprotects a branch, or sets `ref_protected` conditions to pass by creating a protected tag or branch pattern such as `*`. It then runs with a "protected" ref and gets the KMS signature. Fix: use the Developer role and `write_repository`/`read_api` scopes only. Prefer no variable-write scope at all, and split the token used for labels and comments from any administrative one.

- **[severity: blocker] The `id_token` is only as trustworthy as the `aud` and claims the job picks, and the looper controls its own job script.** In GitLab the `id_tokens:` block in `.gitlab-ci.yml` chooses the audience, so a hostile job can request tokens for any audience. WIF must pin the audience to a single value, and the kernel (§4) must pin its own. Add the `ci_config_ref_uri`, `ref_type`, `ref_path` and `pipeline_source` claims to the attribute condition. Reject `merge_request_event` pipelines. Reject `pipeline_source` values other than `schedule` or `api`, since forks and MR pipelines from unprivileged contributors would otherwise get a protected-looking token if the project allows it.

- **[severity: major] `attribute.project_path` is a name, not an identity.** Renaming or transferring a project, or deleting and recreating a group, lets someone with group Owner rights, or anyone who later claims a freed path, inherit the binding (§2, §4). Bind on `project_id` and `namespace_id` too, which are immutable. Keep `tacplus-dev` group owners to a minimum, because a group Owner can add runners, change group variables, and move projects in.

- **[severity: major] The reader app plus read-access to "any" repository is a cross-looper exfiltration path.** Every looper gets a token on every repository (§2). A looper reading private repositories' secrets, or an issue body, can paste it into its own repo's issues or commits. The write scope is per repo, but the data crosses repositories freely. Combined with prompt injection (§5), a poisoned issue in repo A can make looper A summarize repo B's private content into a public place. Restrict the reader to metadata, issues and contents of repositories it needs, and keep it off secret-bearing repositories. Consider egress limits on where loopers can write.

- **[severity: major] Write scope per repository does not stop a looper changing what the repo itself does.** `kernel-looper` can write workflows (if `workflows` permission is ever added), tags, releases, webhooks (if admin), and push to main through the API. A looper that edits `.github/workflows/*` or a deploy script in its own repo can reach whatever the repo deploys to. The "own repository only" claim holds at the GitHub layer but is meaningless if that repository's CI deploys platform-wide secrets. Require branch protection on main on GitHub (PR with review, or a ruleset that the app can't bypass), and don't grant the app bypass. The API-commit route (§2) writes main directly, which is the opposite. Make that a PR with a required check.

- **[severity: major] A one-hour installation token is too long, and is a bearer token that outlives the job.** Request narrower `repositories` and `permissions` in the token creation call, so a leaked token has the smallest scope. Mask it in logs. The job's `id_token` should be short, and the exchange should happen once at job start. Any job artifact or cache that captures the environment leaks the token.

- **[severity: major] KMS IAM granularity.** The binding is per key, so ~30 bindings are easy to get wrong. A single broad `roles/cloudkms.signerVerifier` at project or key-ring level silently gives every looper every key. Use one key per key ring is not enough; grant at key level only, and alert on any IAM policy change in that key ring. The reader key "granted to every project" (§2) means a single wildcard-like binding, so make sure it isn't a `principalSet` on the whole pool. Audit logging (Data Access logs for `AsymmetricSign`) is required to detect abuse, since nothing else records which job signed what.

- **[severity: major] The kicker holds a token that can start pipelines in every project (§3), and starting a pipeline is not "nothing else".** A pipeline trigger lets the holder pass variables into the run (`variables[...]`), and if variable overrides are allowed, the holder can change job behaviour. It also controls which ref runs. If it leaks, an attacker can run any protected-ref pipeline on demand, burn CI minutes, and inject variables. Use pipeline trigger tokens, one per project, rather than one token. Restrict `ci_pipeline_variables_minimum_override_role` to `no_one_allowed` or Maintainer. Pin the ref the kicker triggers. Rotate it, and keep it in a protected variable on a single project, never the group. Alert on pipelines not created by a schedule.

- **[severity: major] Using GitLab's issuer as the root for platform tokens (§4) puts gitlab.com's key management and its multi-tenant claims in your trust domain.** Anyone running a GitLab job on gitlab.com can mint tokens from the same issuer. Only the claims distinguish yours, so every check that omits `namespace_path`/`project_id`, `ref_protected` or `aud` becomes a cross-tenant hole. Replay: the `id_token` is valid until `exp`, so require `jti` single-use tracking in the kernel, or very short `exp`. Set the token to a few minutes and don't let it be written anywhere. Cache the JWKS but honor key rotation. Treat a gitlab.com outage or compromise as an availability and integrity risk for all loopers, and document the break-glass path.

- **[severity: major] Kernel minting a token with `aud` = doppelganger on the strength of a mapping in tenant config (§4) means that config is a privilege boundary.** Whoever edits the `tacplus-dev` tenant config can add a `project_path` and mint a looper principal. If loopers can edit that config (it likely lives in a repo they write to), a looper grants itself or another project access. Keep the config out of looper-writable repositories, and require review.

- **[severity: major] Prompt injection across agents (§5) is not solved by provenance labels.** "Data, never instructions" is a prompt, not a control. Doppelganger relays a message from looper A into looper B's context, and B reads it "at start and between steps". A poisoned issue body in repo A can instruct A to send B a message containing instructions. B has write access to its own repo, so the injection gets code execution there, through a deploy. Provenance says who sent it, not whether it is safe. Controls: mailbox messages are structured (typed fields such as question, contract id, status), never free text that B's model reads as a prompt. Anything free-text is quoted as untrusted and can't trigger tool use directly. Give each looper's tools no capability beyond its repository so injected instructions have little to reach. Rate-limit and log every relay, and have a human review any cross-repo change that follows a message.

- **[severity: major] Doppelganger answering "derived from his rules" is itself an injection and authority-laundering surface.** A looper told "derived from Jody's rules" may treat it as permission. Doppelganger reads a context repo; if any looper can write to that repo, a looper can write Jody's "recorded decisions". Make the context repo read-only to loopers and signed or reviewed, and label derived answers as non-binding in a machine-readable field.

- **[severity: minor] The API-commit approach (§2) loses ordinary git semantics.** The Git data API means the looper's rebase, gates and push flow must be reimplemented, and force-update of refs is available through `PATCH /git/refs`. The Verified badge comes from GitHub signing, not from your KMS key. Whether that is a benefit depends on the branch ruleset.

- **[severity: minor] The mailbox read by "at start and between steps" gives no authentication of which looper a message is for.** Bind each mailbox to the registered `project_path` principal and reject reads from any other.

## Answers to the open questions

1. **No, not as written.** The binding keys on a path and a ref, while the looper controls the pipeline, its token's rights and potentially its branch protections. Take away its ability to change CI config and protections: pin the CI config from an external locked project, bind on `project_id` and `ci_config_ref_uri`, require MRs for main, and give the looper's token Developer role without variable or settings scope. Then the claim holds to the extent that the GitLab project settings are outside the looper's reach.

2. **Prefer the API for main, but through a pull request, not directly.** API commits give Verified status without key handling, and avoid the app needing git credentials. Keep `git push` for working branches only, and make main a PR merged by a ruleset with required checks. Rebase and gates stay in git on the branch. Do not let the app bypass protection. This is both safer and simple enough.

3. **Use one pipeline trigger token per project, or a dedicated bot user at Developer role, held in one protected variable.** Disable variable overrides, pin the ref, alert on pipelines that were not scheduled, and rotate regularly. If it leaks, the damage is bounded to running existing protected pipelines, which is acceptable only when variables can't be injected. A group-wide API token would be a far worse choice.

4. **Sound as a root if tightly constrained, otherwise not.** Require a fixed `aud`, short `exp` (minutes), single-use `jti`, `project_id`, `ref_protected`, `ci_config_ref_uri` and a `pipeline_source` allow-list. Exchange once at job start. Accept that gitlab.com is outside your trust domain and a shared issuer, so every authorization must rely on claims you pin. Have a revocation switch (remove the mapping) and monitor.

5. **Provenance is not enough.** Use typed, structured messages; treat free text as untrusted quoted data; never put it into the looper's instruction channel; reduce each looper's capability so a successful injection reaches little; require human approval for cross-repo effects; log and rate-limit relays. Also protect the context repo of decisions from looper writes.

6. **Roughly 30 apps is manageable but heavy.** Costs are manifest creation (a manual click per app), per-app key creation in KMS, IAM bindings, and rate limits per installation, which are fine at this scale. Key rotation with KMS is a new key version plus uploading the public key to GitHub, which is manual per app. A simpler alternative is one app with per-installation tokens requested for a single repository, where the minting service (not the job) decides which `repositories` to request from the verified `project_path`. This needs one key, and the binding becomes a service check rather than 30 IAM bindings. That moves trust to the minter, which you should then harden and audit. A middle path is a small token broker service that holds one app key, verifies the OIDC claims, and issues tokens scoped to one repository. You lose separate bot names per repository, unless you keep per-repository apps for identity alone.

## What is good and should stay

- No long-lived secrets: OIDC to short-lived tokens.
- Non-exportable KMS keys for app private keys.
- Per-repository bot identities, which make provenance visible.
- Separate read-only app, and one-hour installation tokens.
- Rooting platform tokens in claims-based workload identity with the mapping in tenant config.
- Messages as data, only Jody's recorded decisions settling real calls, and escalation to Jody when doppelganger can't answer.
- Starting with a single repository (kernel) before rolling out.
