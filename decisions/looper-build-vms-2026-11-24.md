# Loopers and builds leave the cluster: one spot VM per project (2026-11-24)

**Status:** decided, and the plan approved (Jody, 2026-11-24: "This can be done in parallel. Getting tacplus its own vm and going is critical"). It runs **in parallel with seatrials**, and the **pilot is tacplus**. Issues: tacplus-dev/looper#238 (looper-vm), #239 (image), #240 (looper.yaml), tacplus-dev/cloud#108 (VMs), tacplus-dev/looper#241 (kicker).
**Supersedes:** `only-vms-are-k8s-nodes-2026-11-04.md` for the **build environment** (the deployment cluster still has only its own nodes), and the looper placement of 2026-11-07 and 2026-11-22 (loopers and builds as pods on the cluster's normal, looper and spot pools).

## Why
On 2026-11-24 the "loopers don't build" rule and in-cluster placement caused most of the day's delay:
- A report's feedback build goes through tacplus-dev/build as about 10 GitLab jobs. On GitLab.com's free plan the project caps at about 500 jobs in active pipelines, and **46 of 82 failed child pipelines between 12:00 and 21:00Z were GitLab refusing to create them**, not red. The managers sent those lands back as red, seatrials' last fix (fleet-seatrials#76) twice.
- Builds wait hours for 6 build slots, and reports can't read their own build logs, so a fix-and-verify cycle takes hours and needs the hub to read the traces.
- Managers and reports share one runner of 17 slots, so merges wait behind reports (cluster#60).

## Decision
1. **One looper+builder per project, on its own spot VM, outside the deployment cluster.** It runs in the CI project (tacplus-ci), never in the cluster that serves deployments. The build environment is kept apart from the deployment cluster.
2. **The agent never blocks, and it has no limit on children** (Jody, 2026-11-24). A parent loop schedules and records state. All the work (builds, tests, model calls, other agents) runs in **child processes, as many as it wants, and children may have children** (trees are fine). **One VM is not limited to one issue:** it works as many of its project's issues at once as it chooses. On a spot preemption notice (about 30 s) the parent signals the tree, each in-flight item pushes its checkpoint, and the parent exits. Every child is safe to run again from the start (a build re-runs, a model call retries).
3. **The VM is completely ephemeral; its disk is only a cache** (Jody, 2026-11-24). Durable state lives where it already does: the work-in-progress branch pushed to the forge and the issue's checkpoint comments. A VM that finds the project's cache disk uses it (the checkout and the build caches; never toolchains); a VM that finds none creates it and starts cold. Either way it reaches the same result, only slower. **It never gets stuck:** a missing, stale, half-written or corrupt cache is discarded and rebuilt, never waited on or repaired by hand. On a preemption notice the parent pushes its checkpoint; nothing is lost that is not also in the forge. No NFS, and nothing shared between projects.
   **Children share the build cache as much as possible** (Jody, 2026-11-24). Two children building at once use one cache on the VM, not a copy each: toolchain and dependency stores shared read-mostly (cargo registry, Go module and build caches, Maven/Gradle, npm), compiler output caches shared where the tool makes that safe (sccache or ccache style, or Bazel-style content-addressed caches), and each child's working tree its own (a git worktree off one shared object store). A cache write that two children race on never corrupts the cache: use tools that lock, or content-addressed stores; otherwise give that one piece a per-child directory. A child never waits long on another's lock, and a corrupt entry is dropped and rebuilt (point 3).
4. **Loopers build for themselves**, as often as they like, and read their own logs. Their builds are feedback only.
5. **No SSH, in any form**, as before. The VMs come from the cloud pipeline (an instance group of 0..1 per project, Container-Optimized OS, the looper as a pinned container, no port 22). **Toolchains live in the container image, never on the VM** (Jody, 2026-11-24): Rust, Java, Go, Node, .NET, Swift and the build tools come in the pinned image (the project's `build.lock` image or one built from it), so the VM's OS holds only the container runtime. The cache disk holds caches, never tools. **The main container has the VM's container socket** (Jody, 2026-11-24), so it runs any container it wants: a child can be a container (a build in a project's own image, a test service, a database for a test). Accepted knowingly: the socket is root on that VM, so anything the main container runs can read whatever the VM holds (its credentials and caches). The blast radius is one project's disposable VM, outside the deployment cluster, and security is not this step's focus (point 7); the future merge system is the control point. Recorded so it is a choice, not an accident: when security becomes the focus, the first items are short-lived, narrowly scoped credentials on the VM and a rootless runtime.. The kicker scales a project to 1 when it has work and to 0 when idle.
6. **Merging:** eventually a project never merges to main itself. It pushes a merge branch and opens a merge request, which a review panel and a separate merge-and-release build system (not yet assembled) handle. **Until then, today's managers and their gated builds stay as the interim merge path**, with no new investment beyond the fixes in flight.
7. **Security is not the focus of this step.** The worker VMs keep today's level; the control point becomes the future merge system.
8. **The deployment cluster shrinks to 3 small VMs** once loopers and builds have left: no spot build pool, no looper pool, no in-cluster CI runners. It holds deployments only.

9. **Each project specifies its own VM, in its repository, and it is right-sized over time** (Jody, 2026-11-24). A file in the repo (for example `looper.yaml`, beside `build.lock` and `gates.yaml`) names the project's ideal looper/builder: machine type (or CPU and memory), disk size, spot or not. It sizes the machine; it never caps the children. The cloud pipeline reads it to make that project's VM. It starts from measured builds (a Rust or Java project needs more than a small Go one) and is adjusted as use is measured: the nightly recap compares each project's measured peak CPU, memory and disk against its spec and files a change, up or down, when they drift. The change lands through that project's normal review like any other code.

10. **An off-the-shelf VM image, started by one generic cloud-init** (Jody, 2026-11-24). The VM runs Google's stock **Container-Optimized OS** (Arm), unmodified. We build no VM images: it comes with the container runtime, a read-only root and automatic OS updates. One cloud-init script, the same for every project, is versioned in tacplus-dev/cloud and set by the pipeline. It (a) reads the VM's identity from instance metadata (its project, the pinned image digest, its spec), (b) mounts the cache disk if present and readable, otherwise formats one or uses a local directory, and never stops for it, (c) pulls the image by digest, and (d) starts the main container as a restarting service, with the project name, the cache and the container socket. It decides no work: the main container reads its project's issues, as loopers do today. **No secrets in cloud-init or metadata:** the container fetches its tokens at start as the VM's own service account (Secret Manager, as the pipelines do). Per-project differences live only in metadata generated from that project's spec file, so every VM boots the same way, and a broken or preempted VM is replaced, never repaired.

11. **The model's credential is a static secret for now** (Jody, 2026-11-24). The VM reads it from Secret Manager (`tacplus-ci/looper-model-token`) as its own account. **Where we need to go** (to be designed in detail, separately): our cluster **issues short-lived tokens to VMs based on their cloud identity**, so no VM holds a long-lived model credential. Not part of this migration.

12. **Amendment (Jody, 2026-11-25): one VM per heavy project, one shared VM per org for the rest.** This replaces point 1's one-VM-per-project. tacplus-dev/tacplus, a heavy build, keeps its own right-sized VM (`looper-vm-tacplus`). Every other tacplus-dev repository is worked by one shared VM (`looper-vm-tacplus-dev`). It has one parent, children across all of its repositories, one idle timer and one cache directory per repository, and it starts at a c4a-standard-4 spot. A repository that turns out heavy is broken out onto its own VM by moving it in the cloud settings. SeaBeam gets its own shared VM when it starts. Point 3's "nothing shared between projects" now means nothing shared between VMs.

## Migration plan (for Jody's approval; nothing changes before it)
Runs in parallel with seatrials (Jody, 2026-11-24). Seatrials keeps first claim on today's worker slots.
1. **Design issue in tacplus-dev/looper:** the parent/child runner (`looper-vm`). It covers the state file format, the preemption handler, child re-runs, the per-project disk layout, and how a project VM takes its issues (the kicker's trigger, or the VM polling its own project).
2. **cloud (tacplus-ci):** an instance-group template per project, the cache disk optional and recreatable (spot, Arm, the machine size read from the project's own spec file, decision point 9), a persistent disk per project, no SSH and no port 22, egress through NAT only, the kicker's permission to resize, and the GitLab/GitHub credentials the looper already uses (Secret Manager through WIF, as today).
2b. **The spec file and the right-sizing loop:** the spec file's format (looper), an initial spec per repository from today's build measurements (each repo, one land), and the recap's drift check.
3. **Pilot on tacplus** beside the current in-cluster looper. Compare time-to-feedback, preemption recovery and cost for a few days.
4. **Roll out the rest**, a few projects a day. Each project's in-cluster report jobs stop as its VM starts.
5. **Managers:** move the interim managers (and the kicker) to a small CI VM, or keep them on GitLab's runners until the merge system replaces them. To decide at step 4.
6. **Shrink the cluster:** remove the spot build pool, the looper pool and the in-cluster CI runners (control, kick, build, build-light, build-report). Size the remaining 3 nodes from the deployments' measured requests (seatrials' 13 services). The infra runner (cloud, cluster and deploy pipelines) moves to the CI VM side, or stays as one small runner. To decide at step 6.
7. **Retire** the runner VMs in jody1-328023 and gitlab-runner-mgr, the last interim VMs.
