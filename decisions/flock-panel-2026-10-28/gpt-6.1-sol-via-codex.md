## Findings

- **[severity: blocker] Sharing one authenticated link does not authorize merging two identities.** An attacker controls an old XID A with a personal credential, then obtains a genuine login to a victim’s organization-managed account through an administrator reset. That account is linked to victim XID B. Automatic merging imports B’s personal credentials and memberships into an identity the attacker can still access through A. Fresh proof of the shared account proves neither control of B’s other mappings nor consent to combine them. Changing the survivor would not fix this authority union. (§§ “Generated helpers,” “Duplicates: detected by generated code”; earlier panel synthesis §1.)

- **[severity: blocker] Partition availability makes the claimed live uniqueness unenforceable.** Partitioned clusters independently create A and B containing the same unique link, return both XIDs, and mint tokens for both. Those duplicates are visible to callers before gossip; merging afterward cannot retract actions already authorized under them. Either ownership changes require coordination, or duplicate identities must remain provisional with explicitly restricted authority. (§§ “Problem,” “Shape,” “Duplicates: detected by generated code.”)

- **[severity: blocker] `merge_entries` and mark dominance admit an order-dependent result.** Cluster X merges B into A while B contains an admin membership. Concurrently, Y removes that membership from B. If the removal reaches X after B’s mark, mark dominance can discard it and leave A’s copied membership intact. If the removal arrives before the merge, A never receives the membership. The same updates produce different survivors’ contents. Losing-entry updates and their causal metadata must continue contributing to the merged identity; copying a snapshot and tombstoning its source is insufficient. (§§ “Generated helpers,” “Deletion marks.”)

- **[severity: blocker] A stale unique-index hit can turn a completed unlink into an irreversible identity merge.** A removes link L; B subsequently acquires L through an authorized flow. A lagging cluster still sees A’s old L when B arrives and merges A with B. The eventual remove-wins result for L cannot undo the combined credentials or privileges. A transient overlap is evidence of a conflict, not sufficient authorization for permanent identity equivalence. (§§ “Duplicates: detected by generated code,” “Field merge rules.”)

- **[severity: blocker] Marks have no defined join for competing targets or deletion reasons.** With A older than B older than C, one cluster can produce `C → A` while another produces `C → B`. Separately, one can produce `USER(C)` while another merges C into A. “A mark always wins” resolves neither pair. Keeping the first mark diverges; selecting one deterministically still leaves unanswered whether deletion must affect A and already-transferred data. Define the merge of marks and the scope of deletion over aliases explicitly. (§§ “Deletion marks,” “Links: a merged entry’s redirect outlives it.”)

- **[severity: major] The redirect cycle argument requires an immutable rank that the schema does not provide.** A fixed total order would prevent cycles if every redirect strictly decreased that order. Here `created_ms` is an ordinary `MIN` field. One cluster can merge A into older B while another accepts a smaller creation value for A and merges B into A. Unless such changes are prohibited, the result is `A → B → A`. Use server-owned, immutable election metadata, distinct from mergeable application timestamps. (§§ “Annotations,” “Generated helpers,” “Links: a merged entry’s redirect outlives it.”)

- **[severity: blocker] Majority acknowledgement does not establish safe deletion of resurrection-prevention metadata.** With copies P, Q and R, P and Q observe a deletion and compact it while partitioned R retains the live entry. If compaction removes the last durable deletion fence, R’s gossip restores the entry. Keeping an irrevocable fence can make payload removal safe; the draft does not specify that distinction. R need not restart, so the returning-copy restriction does not solve this scenario. (§ “Deletion marks.”)

- **[severity: blocker] “Known copies” is not a membership protocol, and catch-up needs an enforceable boundary.** Two partitions can have different peer lists and independently conclude that their own majority acknowledged a mark. A retired copy or restored backup can later reappear with deleted data. Require authoritative membership epochs, durable acknowledgements, fenced replica incarnations, and a defined snapshot/frontier for admission. Health-state absence must not itself authorize retirement or garbage collection. (§ “Deletion marks”; open question 1.)

- **[severity: major] Set and map annotations omit the metadata and update semantics needed for convergence.** An identity tuple tells the implementation which element is involved; it does not distinguish an old add, a concurrent add, and an intentional re-add after removal. Likewise, removing a device-map entry concurrently with updating its nested fields needs an explicit policy. Specify causal contexts, operation identities, key deletion, re-add behavior and metadata preservation across cross-entry merges. The distinction between causal remove-wins and timestamp ordering is substantive, not an implementation detail. (§§ “Annotations,” “Field merge rules,” “Duplicates: detected by generated code”; [CRDT concurrency semantics](https://arxiv.org/html/1805.06358).)

- **[severity: major] `IMMUTABLE` is not a total merge rule when conflicting values are possible.** If two replicas already accepted different values, refusing whichever arrives “newer” leaves each replica holding its own value. Merely surfacing an error also provides no common state. Either conflicting states must be demonstrably unreachable, or the state space must include a deterministic conflict representation that fails closed where necessary. (§ “Field merge rules”; open question 4.)

- **[severity: major] HLC ordering preserves only causality that actually reaches the clock.** A caller reads a future-stamped value from X, then sends a dependent write to Y before gossip reaches Y. Without dependency propagation through the client protocol, Y can assign a smaller timestamp and lose the caller’s causally later write. Persist clock state across crashes, define replica incarnations and counter overflow, and carry causal dependencies across cluster switches. The draft’s claim about writes “made after” another write is otherwise too broad. (§ “Last write wins, on a clock”; [HLC paper](https://cse.buffalo.edu/tech-reports/2014-04.pdf).)

- **[severity: major] Receiver-relative clock rejection can make an accepted write permanently nonconvergent.** A write accepted on a fast-clock cluster may be rejected indefinitely by another cluster using its own wall-clock bound. Clamping its timestamp on receipt instead gives one operation different ordering identities at different replicas. Conversely, accepting it advances receiving HLCs into the future. Such a write dominates unseen concurrent writes; it does **not** dominate every subsequent write once replicas have observed it. Clock admission and recovery must preserve that distinction. (§ “Last write wins, on a clock”; open question 6.)

- **[severity: blocker] Two-person approval cannot provide revocation freshness during a partition.** A revoked administrator can continue minting tokens through an isolated, already-running cluster that has not received the revocation. Two approvers can also approve against stale state. Catch-up on restart changes neither case. State an explicit stale-authorization budget and token lifetime, or require fresh coordinated authority for operations that cannot tolerate that budget. (§§ “Problem,” “Deletion marks,” “Convergence window.”)

- **[severity: major] `MAX` of locally incremented generations does not implement eventual “sign out everywhere.”** Both clusters start at generation 5. X signs out to 6 and subsequently issues a session carrying 6. Partitioned Y later processes another sign-out using its stale 5 and also writes 6. After complete convergence, X’s session still matches 6 despite predating the second sign-out. Use a revocation representation that distinguishes events, or serialize epoch allocation; merging integers with `MAX` does not preserve increment semantics. (§ “Annotations,” `Person.generation`.)

- **[severity: major] Redirect resolution has an unresolved authorization contract.** The draft says marked entries refuse token minting, but also says reads of merged entries follow redirects so old sessions continue working. An old B session can therefore either stop working or become a credential for A, depending on where the mark check occurs. Define operation-specific alias behavior, canonical-subject checks, session assurance and revocation checks, and fail-closed behavior for missing redirect targets. Transparent client compatibility cannot settle these security semantics. (§§ “Shape,” “Deletion marks,” “Links: a merged entry’s redirect outlives it.”)

- **[severity: major] Cross-entry merge requires local atomic durability even without distributed locks.** A crash after persisting B’s mark but before persisting A’s transferred data loses B’s acknowledged state. Persisting only A first can expose duplicate authority after restart. Define an atomic local commit or replayable durable merge operation covering survivor, loser, unique indexes and watch publication. Also specify when an ordinary write is acknowledged; gossip alone is not a durability contract. (§§ “Shape,” “Generated helpers,” “Duplicates: detected by generated code.”)

- **[severity: major] Property-testing individual merge rules does not validate the composed store.** Associativity, commutativity and idempotence of field joins do not establish inflationary updates, correct duplicate-triggered transitions, safe compaction or crash recovery. The membership-removal example above can pass every scalar-rule test. Require whole-store histories covering three-way merges, competing marks, unlink/relink, reordered gossip, crashes, snapshots and membership changes, plus cross-language and mixed-version compatibility tests. (§ “Generated helpers”; [state-based CRDT requirements](https://arxiv.org/html/1805.06358).)

## Answers to the open questions

1. **Choose A for discovery and generated transport, with explicit membership authority.** Health state can locate peers; it must not decide voting membership or retirement. Add authenticated cross-cluster routing through tacplus’s generated S2S clients, membership epochs and replica fencing. Merkle synchronization must include causal metadata, deletion fences and redirects, and support snapshot-plus-catch-up admission. A configured list is acceptable for a deliberately fixed initial deployment.

2. **No: a shared unique element is insufficient proof.** Before adding a link, require fresh, replay-resistant proof for the exact configured issuer and stable subject, bound to the initiating session and intended destination XID. Before combining identities, require explicit authorization over both identities and fresh proof of every mapping whose authority moves, as the earlier panel required. Organization-account control alone is insufficient. Quarantine conflicting ownership claims; record merge evidence durably and rate-limit attempts.

3. **Keep minimal redirect and deletion fences indefinitely initially.** Remove personal payload separately. Finite redirect retention requires an enforceable maximum lifetime for every usable reference, including renewable credentials, plus fenced backups and retired replicas. Majority acknowledgement proves neither reference expiry nor causal stability. After redirect expiry, an old XID must remain permanently unusable rather than becoming an ordinary miss.

4. **Reject conflicting local mutations before acknowledgement; retain replicated conflicts deterministically.** If two conflicting values already exist, preserve both in an explicit conflict state and fail closed for identity or authorization fields. Repair should be an audited operation with defined precedence. “Refuse the newer write” is not a convergence rule for already-divergent replicas.

5. **Keep identity facts, provenance and revocation state; separate disposable telemetry.** Include exact account identifiers, assurance and ownership evidence, membership grants and revocations with proof expiry, device credential status, and merge/deletion provenance. Store secrets elsewhere. Last sign-in can be an advisory monotone maximum, but local inactivity must not trigger irreversible fleet-wide age-out while a partition may contain unseen activity.

6. **Bound clocks at write admission and fence unhealthy writers; do not independently discard admitted writes during gossip.** Use an independent clock-health check, durable HLC state and unique writer incarnations. Define quarantine and recovery for future timestamps already accepted, including how the fleet resumes writes without rewriting operation identities. HLC timestamps should not double as trusted expiry or age-out timestamps.

## What is good and should stay

Declarative, generator-checked merge policies; explicit element identities; random service-owned keys; generated authenticated S2S transport; deletion fences and redirects; and the separation between field-wise merging and whole-entry LWW are sound foundations. Keep partition-tolerant replication for data whose temporary disagreement is acceptable. Keep deterministic survivor selection as a canonicalization mechanism **after** merge authorization.
