## Findings

- **[blocker] Purging an entry once a majority of known copies has seen its mark brings deleted entries back.** (§Deletion marks.) Example: copies {1,2,3}, and B is marked on 1 and 2. Copy 3 is partitioned and still holds B live. 1 and 2 are a majority, so they physically remove B. The partition heals and Merkle catch-up finds that 3 has a key the others lack. 3 ships live B back, and 1 and 2 have no mark left to beat it. The deleted XID now mints tokens again. "Serves nothing until caught up" doesn't help, because the stale copy is the one with the "extra" data. Membership change makes it worse. "Known copies" is a local view, so two sides of a partition count different majorities. A new copy bootstrapped from a pre-mark snapshot also counts toward the majority that permits the purge. The safe rule is that a tombstone is removed only once it is causally stable: every member of an explicit, epoch-numbered membership has acknowledged it. Any copy offline longer than a fixed horizon is wiped and re-bootstrapped, never merged back (Cassandra's gc_grace lesson). For the people table, it is simpler to never remove the mark at all and remove only the payload.

- **[blocker] A local write that hits `(flock.unique)` calls `merge_entries`, which turns the settled "conflicting login is refused" rule into an automatic account merge.** (§Duplicates: "checks it on every local write … On a hit it calls `merge_entries`"; the 2026-10-21 "do not reopen" list: "one key to one XID with a conflicting login refused".) Example: an attacker has a years-old XID P, and phishes the victim's IdP session once. They call "add link (google, victim-sub)" on P. The local unique check finds the victim's V, `merge_entries` keeps the older P, and V is marked `MERGED → P` permanently. V's memberships and devices are absorbed into P, and V's live tokens redirect to P. The attacker's own IdP link now signs in as the victim's identity. A password reset can't undo it, and nothing can undo the mark. This is the 2026-10-21 takeover again, made worse because it is irreversible and done by generated code. A conflict that is visible locally must be refused. Only a duplicate that gossip reveals can be handled automatically, and see Q2 for how.

- **[blocker] Writes to a loser that are concurrent with the merge are dropped, so revoked access comes back.** (§Generated helpers, §Deletion marks: "A mark always wins a merge"; §Links.) The design never says what the survivor absorbs. If it absorbs B's data as one copy saw it, this happens: cluster 1 merges B→A and copies B's memberships, including tenant T, into A. At the same moment, on cluster 2, an admin removes B from T (a `SET_REMOVE_WINS` remove on B's set). The mark wins on B, the removal dies with B, and A keeps T. A revoked membership has come back to life. The same applies to a device added to B, or a device revoked on B. The fix: absorption must be the join of B's full CRDT state, including set tombstones, into A, and every copy re-applies it whenever it sees new state for a marked B. Writes addressed to B after the mark must be redirected to A, not only reads.

- **[blocker] The survivor ordering key can change, the creating copy's clock chooses it, and keys can be ground. The result is two-way marks and a lost person.** (§Annotations: `created_ms … MIN`; §Generated helpers: "older entry, by created time and then key".) `created_ms` is a MIN-merged field, so it can go down. That happens when absorption folds in an older loser's `created_ms`, or when any writer sets it. Example: copy 1 sees A.created=100 and B.created=90 and marks A→B. Copy 2 has already absorbed D (created 80) into A, sees A=80 and B=90, and marks B→A. Marks win and are never undone, so both entries are dead and following the redirect loops. Separately, `created_ms` is the creating copy's wall clock, so a skewed cluster mints "oldest" entries. The random key tiebreak can also be ground: mint many XIDs and keep the one with the lowest key. Any ordering key must be IMMUTABLE and set by flock at creation (an HLC, not a field callers can see). Even then, age is the wrong policy (Q2).

- **[blocker] Gossip has no ordering across entries, so moving a link produces false duplicates that merge two different people.** (§Duplicates: "checks it … on every entry gossip brings in".) A user unlinks Google from A and links it to B. Gossip is per entry, so a copy can receive B's add before A's remove. The unique index hits and `merge_entries(A, B)` runs. If A and B belong to different people (for example after account recovery), they are now one person. That can't be undone, and they share memberships. Fixing this needs causal delivery across entries, or a check that holds off until the element's remove/add context is causally stable (version vectors), or quarantine instead of merge (Q2).

- **[blocker] The `devices` map has no rule and no way to remove an entry, so revoking a lost device gets undone.** (§Annotations: `map<string, Device> devices = 6;`, "merged per entry". §Field merge rules says "a field with no rule is a generator error", which contradicts it.) The per-entry merge is an add-only map. Example: a device is removed on cluster 1, but cluster 2 still has it, and the next anti-entropy round puts it back. Lost-device revocation, the case that matters most, can't be expressed. Maps need explicit key semantics: an add-wins or remove-wins map with causal context, or a per-entry mark.

- **[major] Two copies can put different marks on the same entry, and nothing says how marks merge.** (§Deletion marks: `Mark { reason, merged_into, at }`.) With transitive duplicates (A~B share L1, B~C share L2), arrival order decides the result. One copy records C→A and another records C→B. A `USER` delete on one side meets a `MERGED` on the other. Every copy also emits its own merge, with its own `at`. Without a join for `Mark`, the copies hold different bytes, Merkle digests never agree, and anti-entropy loops forever. The fix is to make the mark a deterministic function of (loser, survivor, reason), with a total order across reasons and across `merged_into` (for example, the survivor at the end of the chain, then the lowest key), and to property-test it.

- **[major] One copy can forge an irreversible, top-priority mark, and receivers don't check it.** (§Deletion marks: "A mark always wins … never undone".) A compromised cluster, a buggy release or a replayed gossip message can mark every XID `MERGED → attacker` within one gossip round, permanently. "The fleet is the trust domain" makes compromise of one cluster bad. Irreversibility plus top priority makes it unrecoverable. Receivers should re-check the merge predicate on their own merged view: the two entries really do share a live unique element, and the survivor is the one the rule picks. A mark that fails the check should be quarantined, not applied. Writes should be signed with the originating copy's SPIFFE identity, so a bad copy can be found and cut off.

- **[major] `EXPIRED` age-out decided from a stale local view permanently deletes active users.** (Background: XIDs aged out after about a year; §Deletion marks.) Cluster 1 hasn't seen cluster 2's recent sign-ins (partition, or a slow or broken gossip path). It sees last-sign-in > 1y, issues `EXPIRED`, and the mark wins everywhere. Expiry must be issued only after every copy has acknowledged a last-sign-in watermark past the cutoff, or it must be a reversible state that is not a mark.

- **[major] `SET_REMOVE_WINS` keyed only by `(flock.identity)` either blocks re-adding an element forever or has no defined meaning.** (§Duplicates: "SET_REMOVE_WINS has to know which add a removal cancels".) If a remove cancels "the element (idp, subject)", unlink-then-relink is impossible forever. To make "remove beats only concurrent adds" work, every add and remove needs causal context (dots or version vectors). Those tombstones need the same causal-stability GC as marks, and the design doesn't say so.

- **[major] Far-future timestamps poison the hybrid clock, and writes from a user who moves between clusters aren't ordered.** (§Last write wins.) An HLC adopts the maximum physical time it has seen. A single message stamped 2030, from a bad NTP state or a hostile copy, pushes every copy's clock to 2030 permanently. From then on only the counter moves, and the bad copy wins every concurrent `LAST_WRITE` for years. Separately, a user edits `display` on cluster 1 and then, seconds later, on cluster 2 before gossip arrives. Cluster 2 hasn't seen the first write, so its write isn't "after" it. If cluster 1's clock is ahead, the user's newer edit loses. The guarantee in §Last write wins holds per copy, not per user. Fix: the client or session carries the last HLC it observed, and every write includes it (see Q6 for bounds).

- **[major] The convergence window is unbounded during a partition, and the two-person rule doesn't address it.** (§Convergence window.) A partitioned copy keeps minting tokens for a revoked, merged or signed-out-everywhere XID for as long as the partition lasts. A second approver is an authorization control and does nothing about propagation. A minting copy needs a bounded-staleness rule: it stops minting if it hasn't heard from a majority within T, or token TTL ≤ T. That is a lease on freshness, not a lock. If this conflicts with "keep serving through a partition", the trade-off should be stated explicitly.

- **[major] Moving state onto flock is not transparent to services, and it reopens the settled "Stratum-first" point.** (§Shape: "transparent to services (Jody)"; 2026-10-21 #6 and the do-not-reopen list.) Callers that read, check, then write ("no XID for this subject, so create one") now create duplicates by design. Read-your-writes across clusters is gone. Entries can disappear under a reader because of a merge. Kernel's Hazelcast-backed state clients may expose CAS or versioned updates that a `LAST_WRITE` table can't honour. tacplus can't check whether a service's correctness depends on linearizability. Moving identity to a store with no locks replaces the Stratum-first, invariant-bearing design the earlier panel endorsed, and the design should say that it does.

- **[major] Schema evolution and mixed-version fleets break convergence.** (§Field merge rules; §Generated helpers.) During a rollout, v1 copies merge unknown field 7 without its rule (they drop it or pick one side). Changing a field's rule, say `LAST_WRITE` → `MAX`, gives two copies different join functions, and the divergence is permanent. Protobuf encoding is not canonical (map order, unknown fields), so Merkle digests can differ for equal states, and anti-entropy churns forever. tacplus can enforce rules here: forbid changing a rule, which is like a wire-compatibility check; refuse writes to a new field until every copy at the fleet version knows it; and hash a canonical encoding.

- **[major] Property tests per rule don't test what actually breaks.** (§Generated helpers: kitchensink, "once per release".) Commutativity, associativity and idempotence of MIN/MAX/LWW in isolation are trivial. The bugs above live in the composition: nested messages, maps, marks, absorption, unique-triggered merges and redirect chains. They also depend on delivery order. Needed: per-schema property tests generated at build time over whole entries plus marks, plus a deterministic multi-copy simulation that checks convergence and the absence of chain cycles and resurrection under random delivery, partitions and purges.

- **[major] A code generator can't check whether `(flock.identity)` and `(flock.unique)` mean the right thing, and a wrong annotation merges masses of people irreversibly.** If identity is marked on `idp` only, or on an email field (reassignable, against panel #8), the first gossip round merges every user of that IdP into one person, with no undo. Add a circuit breaker: if the merge rate exceeds N per window, stop merging and quarantine. Also require an explicit opt-in annotation for auto-merge, separate from `unique`.

- **[minor] `generation MAX` can be set to `u64::MAX`, which permanently disables "sign out everywhere".** The generated client should expose only `bump_generation()`. The design should also say which generation B-tokens are checked against after B→A.

- **[minor] "Caught up" isn't defined.** (§Deletion marks.) Caught up with whom, while writes are still happening? A copy that can reach only a minority either never serves or declares itself caught up against stale peers. One definition: the copy's Merkle root matches a peer, plus it has seen that peer's write watermark as of a recent time.

## Answers to the open questions

1. **Membership and transport.** Use option A for discovery and transport: health state plus generated cross-cluster S2S clients plus Merkle catch-up. Build the cross-cluster client feature once in tacplus for both flock and redo#1. Do **not** use health state as the membership that tombstone GC counts. Health flaps, and kernel's state is a future flock tenant, so flock would depend on itself to bootstrap (and today it depends on Hazelcast, which 2026-10-23 forbids for new kernel work). GC needs an explicit membership list with an epoch, changed by an operator action and replicated as its own record. That is effectively option B for the safety-critical set and option A for routing.

2. **Merges as an attack path.** Sharing a unique element is not enough, as the takeover finding shows. Recommendations:
   - A local unique hit is refused (the settled rule).
   - Adding a link requires fresh proof for that element (IdP `auth_time` within minutes) **and** a step-up proof of an existing link on the target XID, at an assurance level ≥ the new one.
   - A duplicate that gossip reveals is merged automatically only when both entries were *founded* by the shared element within the convergence window. That is the genuine race, and both entries necessarily belong to one principal.
   - Every other overlap becomes **quarantine**: a derived, convergent state ("element live in more than one entry") that refuses to mint through that element and alerts the user or a two-person resolution. The resolution picks the survivor by assurance or by the human, never by age, and stores the proof in the mark.

3. **Redirect stub lifetime.** Keep them forever. A stub is about 40 bytes, pseudonymous and holds no personal data. References to B in audit rows, grants, SPIFFE paths, external systems and backups have no upper bound. This matches 2026-10-21 #7. If they are ever collected, use causal stability across all copies (not a majority), after the longest token or session lifetime, and never while another stub points at B.

4. **`IMMUTABLE` conflicts.** Neither option as worded. "Refuse the newer write" is not a merge function: under concurrency there is no "newer", and copies that refuse differently diverge. Make IMMUTABLE fields set-once by generated code only (no setter), and merge them into a conflict set, which is a lattice (union). An entry whose conflict set has more than one value fails closed for authentication decisions and is surfaced for a human to resolve.

5. **What the people table holds.** Add:
   - `last_sign_in_day` (MAX, at day granularity so sign-ins don't flood gossip).
   - An assurance level and an org/personal classifier per link (2026-10-21 #2 and the org-anchor point).
   - `proved_at`/`auth_time` per membership (#5).
   - An immutable creation HLC.

   Keep audit records, refresh tokens and IdP secrets out of the table. A `USER` mark must shred `display` and all other personal data so the stub stays pseudonymous.

6. **Clock bounds.** Yes, but **delay rather than refuse**. Refusing at some copies and not others diverges. Each copy should:
   - Never advance its HLC's physical part beyond its own clock plus a bound ε, taken from a remote timestamp.
   - Hold incoming writes stamped beyond that bound, without applying or forwarding them, until its own clock catches up. Every copy eventually applies them, so convergence is preserved.
   - Beyond a hard limit (for example an hour), quarantine the sending copy and alarm.
   - Refuse local writes while its own NTP state is unsynchronized.

## What is good and should stay

- flock creates the keys, at random.
- Merge rules are declared in proto, with no hand-written merge, and a missing rule is a generator error (once maps are made to comply).
- Two-argument `merge` with multi-way merging as a fold.
- A hybrid clock instead of raw wall clock.
- First-class deletion marks with a reason and `merged_into`.
- Redirect stubs that outlive the merged entry.
- Detecting duplicates created on both sides of a partition in generated code rather than in callers.
- Keeping the survivor choice out of hand-written code, provided the generated rule isn't "oldest".
- Local reads stay available during a partition.
