## Findings

- **[blocker] `merge_entries` cannot be a join semilattice operation, and "same duplicate found at once converges" is only true for a pair.** (Duplicates, merge) The survivor is the older entry by (created_ms, key), which is a total order, so two clusters merging the same pair agree. But merges are triggered by unique hits on *any* link, and the cross-entry marks are built from local state. Scenario: A, B and C all share overlapping links, and cluster 1 sees A~B while cluster 2 sees B~C before either has the other's data. Cluster 1 marks B→A. Cluster 2 marks C→B. A later merge of B's data into A does not carry C's links, unless merge data is also moved. The result is a redirect chain B→A and C→B, which is fine if the data is moved, but the design never says where the loser's links go. If the links stay on the loser and are removed with it, the survivor loses them. If they are copied, that is a second write that is not covered by the semilattice proof. State what `merge_entries` returns: it must be a deterministic function of the pair, with the unioned fields written to the survivor, and the loser's mark must be a pure function of (loser, survivor).

- **[blocker] The unique rule plus `SET_REMOVE_WINS` plus marks creates resurrection and flapping.** (Annotations, Marks) A mark "never undone" says the merged loser is dead. But its links are still in the gossip stream from copies that have not seen the mark. The unique index sees "idp+subject" on the loser (live from a stale copy) and on the survivor, then fires `merge_entries` again. It is idempotent only if the mark merge is idempotent on `merged_into`. Two different `merged_into` values for the same loser (B→A on one cluster, B→C on another, found at the same time through different links) are not resolved by "a mark always wins". There is no rule for which mark wins, so mark merge is not commutative and copies diverge permanently. Fix: pick the deterministic minimum (by the same order) across `merged_into`, and re-point chains on the next merge. Also `Mark.at` is HLC, so a LAST_WRITE mark rule is unsafe here.

- **[blocker] Redirects can form cycles and are not covered by the order.** (Links/redirects) B→A is decided by the order (created_ms, key). But `created_ms` is `MIN`-merged. Scenario: B was created at t=5 on cluster 1 and A at t=3, so B merges into A. A concurrent create-time merge from a copy that has not yet seen A's created_ms change can produce A→B. Since `created_ms` itself is a mutable-by-merge field (MIN), the "older" relation can change between merges. With a created_ms that is attacker-writable or skewed, the order is not stable and A→B and B→A can both exist. Fix: freeze the ordering key at creation as an `IMMUTABLE` birth stamp, and make redirects point only strictly down the order, which makes cycles structurally impossible. Add a cycle check to the property tests.

- **[blocker] "Keep oldest" is still the account-takeover path here, and the unique-link guard does not prove anything.** (Q2, merge_entries, the earlier panel) The design moves the attack rather than closing it. Scenario: the attacker pre-creates an XID and waits, so it is "older". The victim signs in with IdP X. The attacker then adds the victim's identity link by any route that can reach `add link` (a weak IdP, a self-asserted device key, or an IdP with a reassigned subject). The unique check fires, and the attacker's older entry survives and absorbs the victim's memberships and devices. Worse, because the survivor is picked by generated code and hand-written code "may never choose", the product cannot apply the panel's required survivor-by-assurance rule. Fix: the survivor must be chosen by a deterministic assurance rank that is stored in the entry (and is IMMUTABLE and set by the minting service), with age only as a tiebreaker. Adding a link requires a fresh proof of control, recorded in the link (with level and proof time), and merging must refuse a union that moves anything from a higher-assurance entry to a lower one unless the proof covers every moved mapping. Offline detection at gossip time cannot ask for a proof, so the proof must be carried in the link itself and verified by every copy on ingest.

- **[blocker] Gossip ingest trusts unproved writes.** (Duplicates, Shape) The check runs "on every entry gossip brings in", so any compromised or buggy copy can inject a link that forces a merge of a victim into an attacker's entry, in every cluster. "The fleet is the trust domain" means one compromised cluster owns every account. Needs signed writes with a per-link proof, per-cluster write authority (a cluster may only create or modify the entries it minted, or carry a verifiable proof), and rate limits on merges.

- **[major] Hybrid clock LAST_WRITE is not safe with the stated guarantees.** (Last write wins) "Never reorders a write and one made after it" holds only for causally related writes within a copy's own clock. It does not cover writes on different copies that the second copy has already seen, unless the receive rule `max(local, remote)+1` is applied on merge, which the design doesn't state. A copy with a clock hours ahead wins every concurrent `LAST_WRITE` and, through the receive rule, drags every other copy's HLC forward, so legitimate writes can't beat it for that period. Also a whole-table `LAST_WRITE` (Session) replaces the full entry, so a stale device's field is dropped on every race. Q6 answer below.

- **[major] Deletion marks are monotone but "majority of known copies" makes physical removal non-convergent under membership change.** (Marks) Scenario: five copies, three have seen the mark, and the three remove the data. Two partitioned copies still hold the live entry. When they rejoin, they gossip the entry to the others, who now have no mark to merge it against (the mark was removed with the data) and the entry is resurrected, and anything it names is live again. Also, "known copies" is local state: a copy that has been added but is unknown to the quorum, or a removed copy that comes back with old state, is not counted. Unknown membership means the majority can be computed from stale views. Fix: never remove the mark itself (keep a stub, like the redirect), and only drop the payload. Require acknowledgements from *all* copies in a versioned membership epoch, or fence returning copies by epoch, so a copy that was out longer than the stub lifetime must resync from scratch (and never gossips its entries).

- **[major] A returning copy "serving nothing until caught up" is undefined.** (Marks) Caught up to what? With no coordinator there is no reference point, so a copy cannot know it has all marks. Use anti-entropy digests against a majority and a bound on staleness, or fail closed on tokens that require freshness.

- **[major] The two-person rule contradicts "no locks" and cannot cover revocation.** (Convergence window) Revocations and `generation` bumps ("sign out everywhere") can take unbounded time during a partition, and a stolen device on the partitioned side keeps minting tokens. Mark a revocation class that needs a fleet-wide bound: token lifetimes capped to the convergence window, and a fail-closed rule where a copy that has been isolated for longer than that stops minting.

- **[major] Generated `unique` detection is racy and cannot be exact.** (Duplicates) A local check at write time only sees local state, so concurrent creates in two clusters always create the duplicate and tokens are minted for both entries until gossip converges. Both XIDs can be issued and used (the earlier panel's "a miss treated as absence mints a duplicate"). Nothing here covers the issued tokens, which are covered only by redirects, and the redirect exists only after convergence. Document it as an eventual guarantee, and don't use unique as an authorization invariant.

- **[major] Set rules and identity are underspecified.** (Field rules) `SET_REMOVE_WINS` with the identity of idp+subject means a removed link can never be re-added without a new tag or time, otherwise the remove wins forever. That blocks legitimate re-linking (a user unlinks and relinks the same account), or else requires a per-add unique tag the design doesn't specify. Also, `added_ms` as MIN in an element whose identity is the other two fields is fine, but a remove-wins set without causal context is not a CRDT with arbitrary add/remove interleavings. The `devices` map has no deletion rule either, so removing a device is resurrected by a stale copy.

- **[major] Merge of a nested message with map entries and a mark is not a semilattice unless the mark is a field of the lattice.** (Marks) "A mark always wins and is never undone" is fine as a top element, but the entry and its payload then have to be gone from the merge (the lattice has to treat marked entries as equal regardless of payload). Otherwise two copies with different marks and different payloads compare differently. The property tests need to cover the `Entry` type, including marks, and not just per-field rules.

- **[major] Several things a code generator cannot enforce.** (Shape) (a) The commutativity of `merge_entries` and that survivor selection is stable under field changes. (b) That a hand-written "is duplicate" predicate is a deterministic, symmetric and transitive-enough relation. A non-transitive predicate gives A~B, B~C but not A~C and merge order matters. (c) That services use the redirect (a raw key held in a token is never dereferenced without it). (d) That state clients are "transparent": the hot read path now returns eventually consistent data with redirects, and any caller that assumes a linearizable view (e.g. check-then-write) breaks. (e) Authorization of who may write which field. (f) `IMMUTABLE` conflicts across versions during a rolling schema upgrade, where the generated merge rules differ between releases and copies diverge.

- **[minor] 128-bit random keys prevent collisions but not duplicates.** (Keys) Fine as an identifier, but keys are used as the tiebreaker in the order, and a caller who influences the key (through a weak RNG) controls the survivor. Specify a CSPRNG.

- **[minor] Redirect "chain collapses to the last survivor" at read time is a cost on the hot path and a long-chain DoS.** Compress on write, cap chain depth, and since the order is strictly decreasing, depth is bounded by the number of merges.

- **[minor] Property tests "once per release" on the rules are not enough.** Need generated-entry tests of the whole composite (entry+mark+redirect), and model-checked or fuzzed partitions with message reordering and duplication.

## Answers to the open questions

1. **Membership and transport.** Take option A, but source the membership from a versioned, signed epoch list, not from health state, since health is a liveness view and quorum maths needs a stable membership. Add and remove copies by an explicit epoch change that gossips like any other state. Build the cross-cluster generated clients, since redo#1 needs them too, and use Merkle digests for catch-up. Option B can be the bootstrap.

2. **Merges as an attack path.** No, a shared unique element is not enough. Require a fresh proof of control for every link at add time, stored and verifiable by every copy. Choose the survivor by assurance level then age, store the assurance level in the entry, and do not merge automatically when the two entries have disjoint high-assurance anchors. Hold them as a `PENDING_MERGE` pair that needs the human (a proof of both accounts) or an audited admin approval. Automatic merge should apply only when both entries are in the same assurance class and the proof covers all moved mappings. Rate-limit and audit all merges.

3. **Redirect stub lifetime.** Keep them as long as a token, session or audit reference can name the old key, which is effectively as long as the XID age-out (about a year) plus the maximum token lifetime. Removal requires the same epoch-wide acknowledgement as marks, since a missing stub silently turns a merged identity into "unknown" or, worse, a resurrected live one. Stubs are tiny, so default to keeping them for good.

4. **`IMMUTABLE` conflicts.** Keep both, mark the entry `CONFLICT`, and fail closed for minting from it until a human resolves it. Refusing the newer write makes the outcome depend on arrival order, which breaks convergence, and each copy then keeps a different "first". A deterministic fallback such as the lowest value is acceptable only if it is also surfaced.

5. **What the people table holds.** Add an immutable `assurance level` and `proof time` per link (and per device), `last_seen_ms` (MAX) for the age-out, a `birth` immutable stamp for the order, the audit reference of every merge, and the mark and redirect. Keep roles and anything with an authorization effect out of the table, since a LAST_WRITE or a union merge is the wrong semantics for them. Keep Stratum for those.

6. **Clock bounds.** Yes. Refuse (or clamp and quarantine) writes with an HLC more than a small bound (for example 1 to 5 minutes) ahead of the receiver's physical clock, and never let a refused time advance the local HLC. Alert on a skewed copy. Also give security-relevant fields (marks, `generation`) rules that do not rely on wall time, such as MAX counters, and never use LAST_WRITE for authorization state.

## What is good and should stay

- Flock-owned random keys, which remove create-time key collisions.
- Two-argument `merge` with property tests of commutativity, associativity and idempotence for every rule.
- Marks that dominate, plus redirect stubs that outlive the data (the right fix for the earlier tombstone finding).
- Generator-enforced rules with no hand-written merge, and the split between "hand-written code decides that, the generator decides which".
- Declared `unique` and `identity` in the schema, and honest labelling of what is decided versus draft.
